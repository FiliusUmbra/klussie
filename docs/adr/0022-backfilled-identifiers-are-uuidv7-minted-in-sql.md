# ADR-0022: Backfilled identifiers are UUIDv7 minted in SQL from the row's own creation time

**Status:** Proposed — implemented in Epic 02 WP 02.02; applies to every
backfill in the roadmap, of which this is the first
**Date:** 2026-08-13
**Related:** `../architecture/SUPABASE_ARCHITECTURE.md` §3 §11.4,
`../architecture/DATABASE_ARCHITECTURE.md` §8,
`../IMPLEMENTATION_ROADMAP.md` §3 (the migration pattern) §13 (WP 02.02,
02.03)

## Context

`SUPABASE_ARCHITECTURE.md` §3 is unambiguous:

> **UUIDv7 for every aggregate identifier**, generated by the application
> rather than the database.

WP 02.01 honoured that literally: `identity.identities.person_ref` has no
database default, because a default is the kind of convenience that
quietly becomes the way rows are made.

**WP 02.02 then has to write one row per existing profile, and there is
no application in the loop.** A backfill is a migration — SQL, run once
per environment by the migration runner. There is no engine, no request,
and no client.

The roadmap appears to answer this and does not. WP 02.03 adds UUIDv7
generation at `src/lib/ids.js`, and it is sequenced *after* 02.02 — but
**resequencing would not help**, because a JavaScript generator cannot
supply values to a SQL migration. 02.03 exists for the dual-write path in
02.04, which is a genuinely different need.

So the question is forced, and it is not local to this epic: **eight
further backfills follow** — workspaces and memberships in Epic 03,
properties in 05, locations in 06, assets in 07, documents in 08, and
onward — and every one of them mints identifiers for rows that already
exist.

### Why §3's rule does not decide it

§3 gives its reason, and the reason is what makes the rule mean
something:

> An engine must know an aggregate's identity before it writes, so it can
> emit an event referencing it in the same transaction. Waiting for the
> database to assign one forces either a round trip or a deferred event,
> and the second breaks constraint 5.

**None of that applies to a backfill.** There is no event to emit, no
round trip to avoid, and no transaction whose shape depends on knowing
the identifier first. The rule governs the write path; a backfill is not
one.

The other half of §3 — *why v7 rather than v4* — applies with full force.
Time-ordered identifiers keep inserts local to the right-hand edge of the
index instead of scattering them across every page. A backfill inserting
every existing row at once is precisely the workload that suffers most
from random identifiers.

### The alternatives

**A · Reuse the existing primary key.** `profiles.id` is already a UUID,
already unique, and the backfill would be trivially deterministic.

**Rejected, and not narrowly.** `profiles.id` *is* the Supabase Auth user
id. Making it the person reference would derive the platform's permanent
identity from the authentication provider's — exactly the coupling
§11.4 removes when it requires the auth record and the identity row to be
separable. It would also mean every durable record in the platform
carries an identifier minted by a system the architecture treats as a
replaceable adapter.

**B · `gen_random_uuid()`.** Available, one word, obviously wrong: v4, and
it forfeits the index locality that is §3's stated reason for choosing v7.

**C · A SQL function minting v7 from the row's own creation time.**

## Decision

**Backfills mint UUIDv7 identifiers in SQL, using
`platform.uuid_v7_at(timestamptz)`, passing the source row's own creation
timestamp.**

`created_at` rather than `now()`, and that is the substantive half of this
decision. A v7 encodes its timestamp in the leading 48 bits, so passing
the row's real creation time makes a backfilled identifier **sort exactly
where it would have sorted had it been generated when the row was
created**. Index locality is preserved, and the identifier carries a true
fact rather than the arbitrary moment a migration happened to run.

**The function takes a timestamp and has no no-argument form.** That is
deliberate discouragement: a runtime caller would have to pass `now()`
explicitly, which reads as the mistake it is. `EXECUTE` is revoked from
`PUBLIC` and granted to no role, so **no engine can call it** — only the
migration runner, which owns it. §3's rule stays enforced for every write
path, structurally, while the backfills it was never about can proceed.

Idempotency is separate and unaffected: the backfill inserts only where
no identity exists for the source row, so re-running mints nothing and
changes nothing. **Re-running is a no-op, not a re-mint.**

**This ADR is `Proposed`.** It is implemented against tables that are
empty in every environment. Identifiers are permanent once written (§8:
"Its identifier is permanent and never reused"), so this is cheap to
revise now and never again.

## Consequences

**Makes easier**

- Every backfill in the roadmap has one answer to a question all of them
  ask, instead of eight migrations each inventing one.
- Backfilled rows keep index locality, which matters most for the
  single largest insert any table will see.
- A backfilled identifier's embedded timestamp is true, so ordering by
  identifier and ordering by creation agree — including across the
  boundary between backfilled and later rows.

**Makes harder**

- A function exists that mints identifiers in the database, and §3 says
  the application does that. The grant makes it unreachable by engines,
  but the next person to read the schema must understand *why* it is
  there — which is what this ADR is for.
- Backfilled identifiers are not reproducible. Re-running mints nothing,
  but a backfill that was rolled back and re-run produces different
  values. That is correct — they are new identifiers — and it means a
  rollback of a backfill is not reversible by re-running it.

**Rules out**

- Reusing an authentication provider's identifier as a person reference.
- `gen_random_uuid()` for any aggregate identifier, backfilled or not.
- A no-argument `uuid_v7()` that engines could call at runtime, which
  would make §3 advisory.
