# WP 02.04 — Dual-write identity on signup and profile change

**Epic.** 02 — Identity Engine
**Status.** In review
**Branch.** `epic-02/wp-02.01-identity-table`
**Complexity.** Medium

---

## Goal

New and changed users appear in both structures.

## Migration step

**Step 3 — `dual-write`** (roadmap §3). Both structures are written;
`public.profiles` remains authoritative and nothing reads
`identity.identities`.

## Architecture references

- `SUPABASE_ARCHITECTURE.md` §3 — identifiers generated by the
  application.
- `SUPABASE_ARCHITECTURE.md` §11.4 — the person reference; auth and
  identity are separable.
- `SUPABASE_ARCHITECTURE.md` §4 — what a trigger may do.
- `DATABASE_ARCHITECTURE.md` §8 — the identifier is permanent and never
  reused.
- [ADR-0022](../../docs/adr/0022-backfilled-identifiers-are-uuidv7-minted-in-sql.md)
  — SQL minting for rows the application did not create.

## ADR required?

**No.** No architectural contradiction was found. The roadmap's
*mechanism* for this package is wrong (Finding 1), but the architecture
it implements is not: putting the third write inside the transaction that
already creates the first two is what §3's dual-write step requires, and
the identifier still comes from the application on every path the
application controls.

The SQL fallback is not a new decision either. ADR-0022 already covers
identifiers for **rows the application did not create** — that is
precisely a Supabase-dashboard user or an OAuth signup, where there is no
application in the loop to generate one. No no-argument generator was
added and no grant was widened.

## Scope

**In scope**

- `public.handle_new_user()` — extended to write the identity in the same
  transaction as the auth user and the profile.
- `public.handle_profile_updated()` — new mirror trigger on
  `public.profiles`.
- `src/lib/auth.jsx` — `signUp` and `signInWithOtp` carry a
  `person_ref` generated by `src/lib/ids.ts`.

**Explicitly out of scope**

- **Reading anything from `identity.identities`.** 02.06.
- **Reconciliation.** 02.05, which gates 02.06.
- **Erasure.** 02.07 — but its guard is here, and had to be (Finding 4).
- **`api/_lib/auth.js`.** Listed by the roadmap; it verifies JWTs and
  creates no users (Finding 2).
- **Converting `ids.ts` to JavaScript.** Not needed, and explicitly not
  pre-empted.

## Impact

**Database.** Two functions replaced/added, one trigger added. No schema
change.

**Backend.** None. **Frontend.** Two auth calls carry one extra metadata
field.

**Behaviour.** **None visible.** Signup, magic link, OAuth, sign-in,
profile edit and role selection all behave exactly as before; the
identity write is additional and invisible. Verified by the diagnostic
(profile and contact rows still created), by the client tests (existing
call shapes unchanged), and by loading the app.

## Rollback

```sql
-- Restore the original trigger body from migration 0001, and drop the mirror.
drop trigger if exists on_profile_updated on public.profiles;
drop function if exists public.handle_profile_updated();
-- then re-apply 0001's handle_new_user() definition
```

Revert `src/lib/auth.jsx` to drop the two `person_ref` fields, and delete
the test and the diagnostic.

**No data is lost, and none is orphaned.** Identities already written
remain valid and keep their references; they simply stop being kept in
step, which is the state 02.02 left things in.

## Findings

**1 · The roadmap's mechanism for this package is wrong. The application
does not create users.**

§13 lists `src/lib/auth.jsx` and `api/_lib/auth.js`, which reads as
"add a second write next to the first". There is no first write.
`public.handle_new_user()` — an `AFTER INSERT` trigger on `auth.users`
since migration 0001 — creates the profile and the contact row inside the
transaction that inserts the auth user. The client calls
`supabase.auth.signUp()` and the rows appear underneath it.

Three consequences, and they rule out every client-side placement:

- **A client write cannot be transactional.** It is a separate request
  against an already-committed transaction. A dropped connection, a
  closed tab or a failed redirect leaves an auth user and a profile with
  no identity — the exact inconsistency this package forbids.
- **Two of the three signup paths finish through a redirect.** Magic link
  and OAuth complete on a page load the original caller does not control.
- **The client cannot write to `identity.identities` at all.** WP 02.01
  revoked everything from `anon`, `authenticated` and `service_role`,
  PostgREST does not expose the `identity` schema, and Epic 01 settled
  that it must not. `VERIFY_IDENTITY.sql` check 3 asserts it.

So the write went where the other two already are. The architecture is
not wrong; the roadmap's assumption about this codebase is.

**2 · `api/_lib/auth.js` creates no users, and needs no change.**

It verifies a bearer token and returns a user-scoped Supabase client. It
is called by the two AI endpoints. Nothing in `api/` creates an auth
user, so there is no dual-write to add there.

**3 · `api/` cannot import `ids.ts`, proven rather than assumed.**

WP 02.03 finding 1 flagged this as unverified. It is now verified:

```
import("./src/lib/ids.js")              → ERR_MODULE_NOT_FOUND
import("./src/lib/serviceQuestions.js") → resolves
```

Node's ESM resolver does not map a `.js` specifier onto a `.ts` file;
Vite does, which is why the client works. **This package needs nothing
from `api/`, so nothing was changed** — and per instruction, `ids.ts` was
not pre-emptively converted. It becomes a real decision only when
server-side code first needs to generate an identifier.

**4 · The erasure guard had to be written before erasure exists.**

The mirror updates the identity from the profile. An erased identity
holds no personal data and `identities_erasure_is_complete` refuses a row
that says otherwise. Without `and erased_at is null`, a profile update for
an erased person writes their name back, the constraint rejects it, **and
the rejection fails the caller's profile update** — erasure becoming a
crash in an unrelated screen, months later, in 02.07's name.

Probe 3 reproduces it exactly:
`new row for relation "identities" violates check constraint
"identities_erasure_is_complete"`. Check 6 pins it.

**5 · The mirror fires only when a mirrored attribute changed.**

`markRoleSelected()` writes only `onboarding_role_selected`. Without the
trigger's `WHEN` clause that would bump the identity's `updated_at` on a
change that is not a change to a person — and **WP 02.05's reconciliation
would read the drift as real**. Check 5 pins it.

## Notes

**The identity insert is last in the trigger, deliberately.** If it
fails, the profile insert has already happened in the same transaction
and both roll back together. Ordering it first would make an identity
defect capable of hiding a profile defect.

**`on conflict (auth_user_id) do nothing` rather than a bare insert.**
The unique constraint is what makes a second identity impossible; this
makes an attempt harmless instead of an error that would fail a signup.

**`person_ref` travels in `raw_user_meta_data`, which the user can later
edit** through `auth.updateUser`. It is read once, at insert, so editing
it afterwards changes nothing — the identity keeps the reference it was
given.

**Two of five auth entry points carry a reference; the other three are
correct without one.** `signUp` and `signInWithOtp` create users.
`signIn` does not. `signInWithOAuth` cannot carry metadata and has no
provider configured (`docs/operations/AUTH_PROVIDER_SETUP.md`); when one
is enabled, those signups take the minted path, which check 2 already
covers.
