# WP 02.06 — Switch profile reads to the identity engine

**Epic.** 02 — Identity Engine
**Status.** In review
**Branch.** `epic-02/wp-02.01-identity-table`
**Complexity.** High

---

## Goal

Identity becomes authoritative for display information — and a user
cannot tell.

## Migration step

**Step 5 — `switch reads`** (roadmap §3). **The only behaviour-changing
package in this epic and the only one that can regress.** Writes are
untouched: `public.profiles` is still written by everything that wrote it
yesterday.

**Gate:** `RECONCILE_IDENTITY.sql` passes over 4 real rows on staging
(WP 02.05). Roadmap §8 permits the switch only with that in hand.

## Architecture references

- [ADR-0023](../../docs/adr/0023-identity-display-resolution-versus-row-visibility.md)
  — **accepted**, and the reason this package has two operations rather
  than one table read.
- `SYSTEM_ARCHITECTURE.md` §6.1 — the Identity engine's public contract:
  *"Resolve an internal person-reference to display information, subject
  to erasure."*
- `SUPABASE_ARCHITECTURE.md` §11.1 — no field-level security anywhere.
- `SUPABASE_ARCHITECTURE.md` §11.4 — erasure; the reference resolves to
  nothing.

## Scope

**In scope**

- `public.current_identity()` and
  `public.resolve_identity_display(uuid[])`.
- `loadProfile` merges identity attributes over the profile row.
- `fetchPublicProInfo` resolves names and avatars.

**Explicitly out of scope**

- **Retiring `public.profiles` or `public.profile_contacts`.** ADR-0023:
  step 6 is not reachable in this epic.
- **Contact channels for anyone but the caller.** Still
  `profile_contacts` and its three bilateral policies.
- **Writes.** Unchanged.

## Rollback

Revert `src/lib/auth.jsx` and `src/lib/pros.js`. The functions can stay —
nothing else calls them. **One code change, no data change**, which is
the property roadmap §3 requires of step 5.

## Findings

**1 · The resolvers live in `public` because a migration cannot expose
the `identity` schema.**

ADR-0023 assumed an own-row RLS policy with the client reading
`identity.identities` directly. `pgrst.db_schemas` is not set on the
`authenticator` role on this project — exposed schemas are configured
outside the database — so a migration setting it would be ignored or
fight the dashboard.

`SECURITY DEFINER` functions in `public` are the established alternative
(ADR-0004's `emit_domain_event`). **The outcome is stricter than the ADR
planned for:** its stated cost — *"identity.identities becomes reachable
from the client API surface for the first time"* — is not paid. Check 4
asserts no client role has `USAGE` on the schema or `SELECT` on the
table. Recorded in the ADR under "As implemented".

**2 · A probe found a gap where I had asserted the opposite.**

My own test file called `onboarding_role_selected` and
`home_tour_completed_at` load-bearing. Removing `...profile` from the
merge — dropping them, `id` and `created_at` from every consumer of
`useAuth().profile` — **broke no test.**

It would not have surfaced in a test run. It would have surfaced as the
role-selection screen and the first-login tour reappearing for every
existing user on every load: the two surfaces whose entire job is to
appear exactly once. `identityProfileMerge.test.jsx` now covers it, and
re-running the probe fails two assertions.

**Writing "this is load-bearing" in a comment is not the same as testing
it**, and the probe is what found the difference.

**3 · The first implementation leaked erased people's names, and the
test caught it.**

`fetchPublicProInfo` branched on whether the resolver returned a row for
that person. When the resolver **answers** and has no row — which is
precisely erasure — that fell through to the embedded profile and
displayed the name anyway.

The branch has to be on whether the resolver was *available*, not on
whether it had a row. A resolver that answered with no row is saying the
person resolves to nothing (§11.4); falling back there puts an erased
person's name back on screen, which is the one outcome erasure exists to
prevent.

**4 · Revoking from `PUBLIC` is not enough on Supabase.**

Supabase ships `alter default privileges in schema public grant all on
functions to anon, authenticated, service_role`. That grants `anon`
`EXECUTE` **by name**, and it survives `revoke ... from public` untouched.

Both resolvers were callable by anonymous visitors until an explicit
`revoke ... from anon` was added — on `SECURITY DEFINER` functions
reading every person's row. Found by testing the boundary rather than by
reading the migration. Check 3 keeps it closed.

This is the same shape as Epic 01's finding about default privileges
being right nearly everywhere and wrong at each exception — except these
defaults are Supabase's, not ours, and they apply to every function any
future migration adds to `public`.

**5 · The first version of check 2 passed while checking nothing.**

A `returns table (...)` function has `record` as its return type; the
output columns live in `proargnames`/`proargmodes`. Reading them off a
composite type via `pg_type.typrelid` returns `NULL` — and a `NULL`
compared against an expected array is a failure only because I compared
with `is distinct from`. Had it been written as an equality check, the
privacy boundary would have been "verified" by a query that finds nothing.

## Notes

**Both paths fall back when the resolver is unavailable**, and that is
about deployment rather than drift: production has none of Epic 02's
migrations, so the RPC does not exist there. Falling back to a name that
is still correct beats rendering every professional as `"Pro"`. Drift
between the two sources is a different problem and the one
`RECONCILE_IDENTITY.sql` exists to make impossible — so both fallbacks
warn rather than passing silently.

**`loadProfile` still reads `public.profiles`.** Not a hedge — the
identity row has no column for `onboarding_role_selected` or
`home_tour_completed_at`, by WP 02.01's deliberate decision.

**The resolver takes auth user ids, not person references.** The
application still keys professionals by their auth user id everywhere;
changing that key is Epic 03's business, and doing it here would have
made this package a refactor as well as a read switch.
