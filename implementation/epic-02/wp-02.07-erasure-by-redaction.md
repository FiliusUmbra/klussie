# WP 02.07 — Implement erasure by redaction

**Epic.** 02 — Identity Engine
**Status.** In review
**Branch.** `epic-02/wp-02.01-identity-table`
**Complexity.** High

---

## Goal

Erasing a person leaves durable history intact.

## Migration step

**Not one of the six.** Erasure is a capability the platform did not have,
not a stage in moving an aggregate. It is additive: nothing calls it.

## Architecture references

- `DATABASE_ARCHITECTURE.md` §8 — *"the hardest question in the
  document"*, and its answer: personal data separated from the durable
  record.
- `SUPABASE_ARCHITECTURE.md` §11.4 — erasure redacts; the reference
  remains valid as a key and resolves to nothing.
- `SUPABASE_ARCHITECTURE.md` §5 — no cascading deletes anywhere.
- `SUPABASE_ARCHITECTURE.md` §8, `DATABASE_ARCHITECTURE.md` §33 — audit
  captures *"every export or erasure"*; audit rows arrive through a
  privileged path.
- `SYSTEM_ARCHITECTURE.md` §6.1 — the engine executes erasure "by
  redacting personal data while leaving durable references intact".

## ADR required?

**No.** Erasure by redaction is decided in three frozen documents. The
one judgement call — also redacting `public.profiles` and
`public.profile_contacts` — follows from ADR-0023 leaving both in place
through this epic: redacting one of the three tables that hold a person's
attributes would make the operation a statement rather than an erasure.

## Scope

**In scope**

- `identity.erase_person(person_ref, actor_type, actor_ref, authority)`.
- Redaction across all three tables holding personal attributes.
- An audit record, per §33.

**Explicitly out of scope**

- **`api/_lib/identity.js`.** The roadmap lists it; nothing can call the
  function, so a module wrapping it would be dead code. See Finding 1.
- **An erasure request flow.** Roadmap §13: erasure is not exposed to
  users.
- **`public.pro_profiles`.** See Finding 3 — a legal question, not an
  implementation one.
- **Deleting the auth record.** See Finding 2.

## Findings

**1 · `api/_lib/identity.js` was not written, because it would be dead
code.**

The roadmap lists it. Nothing can call `erase_person` — `EXECUTE` is
revoked from every role, deliberately, because erasure has no request
flow and is not exposed to users. A JavaScript module wrapping an
unreachable function would be code with no caller and no test that
exercises anything real.

This is the **fifth** package where the roadmap's file list assumed
application code can reach a non-`public` schema (01.06, 01.07, 02.04,
02.05, and now this). The pattern is consistent and worth stating once
more for whoever plans Epic 03: **the roadmap was written before Epic 01
decided that application code does not reach the new schemas**, and its
file lists have not caught up.

**2 · Deleting an auth user would destroy the person's entire history,
and both sides of every conversation.**

`public.profiles` is the parent of **nine** `on delete cascade` foreign
keys — `conversations`, `messages`, `reviews`, `service_requests`,
`household_items`, `reports`, `pro_profiles`, `profile_contacts`,
`ai_usage_log` — and `profiles.id` itself cascades from `auth.users`.

So the intuitive implementation of erasure is catastrophic, and it is
catastrophic beyond the person requesting it: deleting one account
deletes messages the *other* party wrote.

`SUPABASE_ARCHITECTURE.md` §5 says *"No cascading deletes anywhere. Not
one."* and §11.4 says *"Deleting an auth user must never cascade."* **The
current schema violates both**, and has since migration `0001`. This
package does not fix that — it routes around it by never deleting — but
the cascade remains, and anything that deletes an auth user (the Supabase
dashboard's delete button, the admin API) will still take the history
with it. **Raised for the epic that retires these tables.**

**3 · `public.pro_profiles` is not redacted, and that is a legal
question rather than an oversight.**

It holds `business_name`, `vat_number` and `bio`. For a registered
company those are public trading details. For a `flexi` sole trader — the
majority of this marketplace — `business_name` is frequently the person's
own name, and a VAT number identifies an individual.

Redacting it would erase a business's public record; not redacting it may
leave a person's name behind. **Deciding which is not an implementation
detail**, so the migration leaves it and says so. The erasure-request
epic needs an answer before erasure is offered to anyone.

**4 · The audit record is the first row ever written to
`platform.audit_records`.**

Epic 01 built it and left the write path unallocated; §33 requires an
audit record for *"every export or erasure"*, so this package needed one
and could write it: `erase_person` is `SECURITY DEFINER` and owned by the
table's owner, which is precisely §8's *"audit rows arrive through a
privileged path."*

It also exercises ADR-0021's nullable workspace for the first time —
erasure is a platform-scoped action, so the record has no workspace. That
decision was made in the abstract in WP 01.05 and has now been used for
what it was designed for.

**5 · The order of two statements is load-bearing, and the reason is WP
02.04.**

Redacting `public.profiles` fires the dual-write mirror, which copies
profile attributes onto the identity row `where erased_at is null`.
Marking the identity erased **first** is what makes the mirror skip.
Reversed, the mirror writes nulls onto an already-null row — harmless
today, and it would stop being harmless the moment the mirror carries a
column the redaction does not. The structural test pins the ordering
rather than the outcome, because the outcome is currently identical.

## Notes

**The audit record names the reference and never the person.** Writing
the erased name into an append-only permanent table would undo the
erasure in the act of recording it. Check 4 asserts the record does not
contain the name, and the probe that captured it before redaction fails
exactly there.

**Erasure is idempotent and returns whether it did anything.** It is
requested by people under stress and retried by systems under load; a
second attempt must not fail, and must not write a second audit record
claiming a second erasure happened.

**It refuses an erasure with no actor or no authority.** §33 requires
both. An erasure nobody is accountable for is not auditable, and an
unauditable erasure is worse than none — it is a deletion with a
paper trail that says nothing.
