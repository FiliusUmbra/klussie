# WP 02.02 — Backfill identities from existing profiles

**Epic.** 02 — Identity Engine
**Status.** In review
**Branch.** `epic-02/wp-02.01-identity-table`
**Complexity.** Medium

---

## Goal

Every existing user has an identity row.

## Migration step

**Step 2 — `backfill`** (roadmap §3). The new structure is populated and
still unused. `public.profiles` remains authoritative and remains
written.

## Architecture references

- `SUPABASE_ARCHITECTURE.md` §3 — UUIDv7, application-generated, and the
  reason that rule exists.
- `SUPABASE_ARCHITECTURE.md` §11.4 — the identity row is the only place
  personal data lives; the auth record and the identity row are
  separable.
- `DATABASE_ARCHITECTURE.md` §8 — identity attributes include contact
  channels; the identifier is permanent and never reused.
- `IMPLEMENTATION_ROADMAP.md` §3 — backfills are idempotent and
  re-runnable.

## ADR required?

**Yes, and one was written first:**
[ADR-0022](../../docs/adr/0022-backfilled-identifiers-are-uuidv7-minted-in-sql.md).

WP 02.01 finding 2 raised the question; investigating it showed the
roadmap's apparent answer is not one. §3 puts identifier generation in the
application, and a backfill has no application in it. **Resequencing
02.03 ahead of this package would not have helped** — 02.03 delivers a
JavaScript generator at `src/lib/ids.js`, and JavaScript cannot supply
values to a SQL migration. 02.03 exists for the dual-write path in 02.04,
which is a genuinely different need.

The decision is also not local: **eight further backfills follow** —
workspaces, memberships, properties, locations, assets, documents — and
every one mints identifiers for rows that already exist. Identifiers are
permanent once written (§8), so it is cheap now and never again.

## Scope

**In scope**

- `platform.uuid_v7_at(timestamptz)` — the backfill minter, executable by
  no application role.
- The backfill itself: one identity per profile, contact details folded
  in, real creation time preserved.
- `supabase/diagnostics/VERIFY_IDENTITY_BACKFILL.sql`.

**Explicitly out of scope**

- **Keeping the two in step.** A profile changed after this runs is not
  reflected — that is the dual-write in 02.04, and proving they agree is
  02.05's reconciliation, which gates the read switch in 02.06.
- **Any read or write path.** Nothing reads the backfilled rows.
- **`public.profiles`.** Untouched.
- **Seeding staging.** See Findings 2 — raised, not fixed.

## Impact

**Database.** Backfill. One function, one insert. Zero rows inserted on

**Backend.** None. **Frontend.** None.

## Tests

`supabase/migrations/__tests__/identityBackfill.test.js` — eight
structural assertions. Each of the three that matter guards against an
edit that looks like a simplification:

| Test | The edit it catches |
|---|---|
| Inserts only profiles that have no identity yet | Dropping the guard makes the backfill run-once, which §3 says cannot be trusted |
| Mints a new person reference rather than reusing the auth user id | `p.id` is shorter than calling the minter and couples identity to authentication |
| Mints from the row's own creation time, not `now()` | Reads as a tidy-up; throws away the reason for a timestamped identifier |

`supabase/diagnostics/VERIFY_IDENTITY_BACKFILL.sql` — seven checks.
**Checks 3–6 build their own population**, because staging has no
profiles and "every profile has an identity" is true and worthless
against an empty table:

| Check | What it proves |
|---|---|
| 1 | Every real profile has an identity — and says out loud when the environment has none |
| 2 | The minter exists, takes a timestamp, and **no application role can execute it** |
| 3 | Version 7, correct variant, the embedded timestamp decodes to exactly what was passed, and ordering follows time |
| 4 | Three synthetic profiles map correctly: attributes, contacts from the separate table, real `created_at`, a **fresh** v7 reference, and a sparse profile not skipped |
| 5 | Re-running inserts nothing **and re-mints nothing** — a re-mint would leave anything holding the old reference pointing at nothing |
| 6 | A profile created after the backfill is picked up by re-running it — which is what makes the gap before 02.04 survivable |
| 7 | Nothing was left behind |

## Rollback

```sql
delete from identity.identities where erased_at is null;   -- the backfilled rows
drop function platform.uuid_v7_at(timestamptz);
```

Then delete the migration, the diagnostic and the test, and remove `0026`
from `supabase_migrations.schema_migrations` in any environment it
reached.

**One caveat, stated because it is the opposite of what "re-runnable"
suggests.** Rolling this back and re-running it produces **different**
person references. That is correct — they are new identifiers — but it
means the rollback is not reversible by re-running, and anything that had
stored a reference in between would be left pointing at nothing. Nothing
does yet. After 02.04 dual-writes, it will.

*(`delete` works here only because no role has `DELETE` on the table —
this is the owner acting deliberately, which is the intended shape.)*

## Findings

**1 · The roadmap's answer to the identifier question is not an answer.**

WP 02.01 finding 2 read as a sequencing problem — 02.03 provides UUIDv7
generation and comes after 02.02 — and the obvious fix is to swap them.
Investigating showed the swap changes nothing: 02.03 delivers
`src/lib/ids.js`, and **JavaScript cannot supply values to a SQL
migration**. The two packages address different needs and always did.
ADR-0022 records the real decision.

**2 · Staging has no profiles, so the acceptance criterion is vacuous
there.**

`public.profiles` holds **zero rows**. ENVIRONMENTS.md §4.4 calls for a
seeded customer and a seeded professional, and Epic 00's completion
record lists test accounts among what was verified — but the table is
empty, so either they were never created or they did not survive.

This matters beyond one package. **Every backfill in this roadmap will be
"verified" against an empty database** unless it is fixed, and roadmap §3
names backfills as the step whose failure mode is data rather than a
revertable read path. Epic 03's workspace backfill is explicitly the
highest-risk item in the risk register.

Worked around here rather than fixed: the diagnostic builds its own
population and rolls it back. **That is strictly stronger than counting
zero against zero and strictly weaker than real seeded accounts** — it
tests the mapping, not the data. Fixing it means seeding staging, which is
a WP 00.06 obligation and not this package's to absorb. **Raised.**

**3 · `EXTRACT(field FROM source)` cannot be schema-qualified.**

Under `set search_path = ''` every function reference must be qualified,
and `pg_catalog.extract(epoch from p_at)` is a syntax error — `EXTRACT`
is SQL syntax, not a function. `date_part` is the function form of the
same operation and qualifies normally.

**This is the second instance of the same trap**, after `coalesce` in
migration 0023, and both were found by running the code rather than by
review. The pattern is worth naming: *the SQL constructs that look like
functions and are not*. The migration says so at the call site, because
the natural reaction to the error is to remove the empty `search_path`
rather than the qualification — which would silently give up the
protection the empty path provides.

**4 · The diagnostic embeds a copy of the backfill statement.**

Checks 4–6 re-implement the `insert … select … where not exists` rather
than invoking the migration, because a diagnostic cannot run one file of
a migration chain. **If the migration's mapping changes and the copy does
not, checks 4–6 would verify the old mapping and pass.** Check 1 is the
guard that still tests the real thing, and the structural test pins the
migration's own shape — but the duplication is real.

The clean fix is to extract the backfill into a callable function both
sides invoke. That is a design change the roadmap did not ask for, and it
would make a one-time migration permanently callable. **Raised rather
than taken**, because 02.05's reconciliation may want exactly such a
function, and that is the package where the question belongs.

## Notes

**Contact details move onto the identity row.** `public.profile_contacts`
exists so RLS can hide email and phone until a booking exists; §11.4
makes the identity row the only identity-scoped aggregate holding
personal data, and §8 counts contact channels among its attributes. The
backfill folds them in with a left join — a profile without contact
details is ordinary, not a reason to skip it.

**`where not exists` rather than `on conflict do nothing`.** The latter
would also swallow a unique violation arising from an unrelated cause.
This says exactly what it means: insert the profiles that do not yet have
an identity.

**The minter's signature is the enforcement.** Taking a timestamp with no
no-argument form means a runtime caller would have to write
`platform.uuid_v7_at(now())`, which reads as the mistake it would be —
and `EXECUTE` is revoked from `PUBLIC` and granted to nobody, so no engine
can write it at all.
