**Epic.** 02 — Identity Engine
**Status.** In review
**Branch.** `epic-02/wp-02.01-identity-table`
**Complexity.** Low

## Goal

Application-generated, time-ordered identifiers are available.

## Migration step

**Not a migration.** No data, no schema, no read switch. A new leaf
module with no dependents.

## Architecture references

- `SUPABASE_ARCHITECTURE.md` §3 — UUIDv7 for every aggregate identifier,
  generated by the application; **and both reasons it gives**, which are
  what the implementation is shaped by.
- `SUPABASE_ARCHITECTURE.md` §12 — the emission helper takes an
  `event_id` from its caller, which is what this module exists to supply.
- [ADR-0022](../../docs/adr/0022-backfilled-identifiers-are-uuidv7-minted-in-sql.md)
  — the boundary between this generator and the SQL minter used by
  backfills.

## ADR required?

**No.** §3 decides the format and where generation happens; RFC 9562
decides the layout. The one judgement call — a monotonic counter in
`rand_a` rather than random bits — is not a choice between reasonable
alternatives. §3's stated reason for choosing v7 over v4 is index
locality, and random `rand_a` forfeits it for exactly the burst writes
where it matters. RFC 9562 §6.2 names the counter as the method for
this. Recorded in the module rather than as an ADR.

## Tests

`src/lib/__tests__/ids.test.ts` — ten assertions. The shape checks are
the cheap half; **four of the ten are about the awkward cases**, because
the ordering guarantee is the only reason §3 chose v7 at all:

| Test | What it proves |
|---|---|
| Strictly increasing within a single millisecond | The guarantee that makes v7 worth choosing. Every id shares a timestamp, so ordering comes entirely from the counter |
| Borrows a millisecond rather than wrapping when the counter is exhausted | ~4096 ids in one millisecond guarantee an exhaustion. Wrapping emits a value **below** its predecessor — the one outcome ordering cannot survive |
| Never issues a value below one already issued when the clock goes backwards | NTP corrections and suspended VMs both do this. Trusting the clock would write an id below one already stored |
| Unique under interleaved async callers | JavaScript's "concurrency" is interleaving — precisely the shape of an engine serving many requests, and where a generator holding state could hand out a duplicate |

Plus: canonical format; version and variant per RFC 9562; the embedded
timestamp is the millisecond given; ordering holds across milliseconds;
uniqueness across 20,000 unpinned values; and the counter seed is not
fixed at zero.

## Findings

**1 · The generator is TypeScript, and the only existing cross-boundary
import is JavaScript. Unverified for server-side use.**

`api/ai-intake.js` imports `../src/lib/serviceQuestions.js`, which is a
real `.js` file — that is the only precedent for `api/` reaching into
`src/lib`. Vite resolves a `.js` specifier to a `.ts` file (proven in WP
00.04), but **`api/` is not built by Vite**; Vercel builds those
functions separately, and whether its Node runtime resolves
`../src/lib/ids.js` to `ids.ts` from a JavaScript api function has not
been tested here.

Nothing imports the module, so nothing is broken. **It matters for
02.04**, whose dual-write may need identifiers server-side. If it does
not resolve, the fix is a rename and stripping the type annotations —
minutes, and no behaviour to preserve. **Raised rather than pre-emptively
downgraded**, because §13 sanctions TypeScript and the client side
definitely works.

**2 · There are now two v7 implementations, and they must agree
forever.**

This module generates identifiers at runtime;
`platform.uuid_v7_at(timestamptz)` mints them in SQL for backfills
(ADR-0022). Both write the same 128-bit layout, and rows from both end up
in the same index — a backfilled reference and a later runtime one must
be mutually orderable or the locality argument fails at exactly the
boundary between them.

This is duplication of a **specification**, not of business logic, and it
is unavoidable: one runs where there is an application and one runs where
there is not. Both are pinned by tests that check version, variant and
decoded timestamp independently — `ids.test.ts` here, and
`VERIFY_IDENTITY_BACKFILL.sql` check 3 there. Recorded so the pair is
known to be a pair.

**3 · The counter is seeded randomly, which is a privacy property rather
than a correctness one.**

Seeding at zero would be simpler and would still be monotonic. It would
also let anyone holding two identifiers issued in the same millisecond
read off how many were issued between them — a volume signal §3 already
objects to when it rejects bigint sequences for "leaking volume and
ordering to anyone who sees one". Seeding in the counter's lower half
keeps roughly two thousand increments of headroom before the borrow path
is needed.

## Notes

**The clock is injectable, and is not a way to backdate an identifier.**
`uuidv7(nowMs)` matches the house pattern (`timeGreeting(t, now)` in
`src/home/useHomeContext.js`, injectable "so a test can pin the band
without mocking the global clock"). The generator still never issues a
value below one it has already issued, whatever it is told the time is —
which is why the clock-went-backwards test asserts the *timestamp* is
unchanged, not merely that the string sorted correctly.

**Every test re-imports the module.** The generator holds the last
timestamp it issued, so a test pinning an earlier millisecond than its
predecessor would exercise the clock-went-backwards path by accident
rather than on purpose.
