# WP 02.01 — Create the identity table (add)

**Epic.** 02 — Identity Engine
**Status.** In review
**Branch.** `epic-02/wp-02.01-identity-table`
**Complexity.** Low

---

## Goal

The identity structure exists; nothing reads or writes it.

## Migration step

**Step 1 — `add`** (roadmap §3). Pure addition. `public.profiles` is
untouched and remains the application's source of truth.

## Architecture references

- `DATABASE_ARCHITECTURE.md` §8 — the identity aggregate, and the erasure
  decision it calls *"the hardest question in the document"*: personal
  data separated from the durable record, which refers to a person by a
  stable internal reference.
- `SUPABASE_ARCHITECTURE.md` §11.4 — the person reference; erasure by
  redaction; **"deleting an auth user must never cascade"**; and the two
  rules imposed on every migration.
- `SUPABASE_ARCHITECTURE.md` §3 — UUIDv7, application-generated.
- `SUPABASE_ARCHITECTURE.md` §5 — no foreign key from a durable record to
  identity; no cascading deletes anywhere.
- `SYSTEM_ARCHITECTURE.md` §6.1 — what the Identity engine owns, and the
  longer list of what it does not.

## ADR required?

**No.** Every property of this table is stated in a frozen document:
the person reference, application-generated identifiers, no cascade from
auth, no foreign key inward, erasure by redaction, mutable attributes.

The one judgement call — **no foreign key to `auth.users` at all**,
rather than one with `on delete set null` — is not genuinely open. §11.4
requires the auth record and the identity row to be *separable*, and a
foreign key must choose an `on delete` behaviour: `cascade` destroys
identity with authentication, `restrict` makes an auth deletion fail,
`set null` still lets the auth provider reach into this schema. Absence
is the only option that makes "never cascade" structural rather than a
correctly-chosen clause. Recorded here rather than as an ADR because
there is no reasonable alternative to reject.

## Scope

**In scope**

- `identity.identities` — person reference, auth link, personal
  attributes, erasure marker.
- Constraints: complete erasure, valid locale, one identity per auth
  user.
- `UPDATE` granted (mutable class); `DELETE` granted to nobody.
- RLS enabled, no policies.
- `supabase/diagnostics/VERIFY_IDENTITY.sql`.

**Explicitly out of scope**

- **The backfill** — WP 02.02. This table is empty.
- **UUIDv7 generation** — WP 02.03. The column deliberately has no
  default. See Findings 2.
- **Any read or write path** — 02.04 dual-writes, 02.06 switches reads.
- **The erasure path itself** — 02.07. Only the structure it needs is
  here.
- **RLS policies.** The policy letting a person read their own row is
  02.06's decision, made with the read path in front of it.
- **`public.profiles`.** Untouched, still authoritative, still written.

## Impact

**Database.** Additive. One table, four constraints, one grant, RLS
enabled. No foreign key in either direction.

**Backend.** None. **Frontend.** None.

**Behaviour.** None — this package is behaviour-preserving. Nothing reads
or writes the table, no client role can reach it, and the application's
identity path is unchanged.

## Tests

`supabase/migrations/__tests__/identity.test.js` — nine structural
assertions. The two that carry the epic's hardest rules:

| Test | What it protects |
|---|---|
| Declares no foreign key, in either direction | §11.4's first rule. **The violation is the obviously correct thing to write** — a reviewer expects to see a foreign key on `auth_user_id`, and it makes erasure impossible or destructive |
| Refuses an erasure that left personal data behind | Checked field by field. A redaction that missed a column looks like an ordinary sparse row, and the defect is unlawful rather than merely wrong |

Plus: no default on the person reference; an identity may exist without
an auth user; `UPDATE` granted and `DELETE` withheld; RLS on with no
policy; nothing granted to client roles; `public` untouched; re-runnable.

`supabase/diagnostics/VERIFY_IDENTITY.sql` — five checks against staging.
**Check 2 is the one that will keep mattering:** it asserts that *nothing
anywhere in the database* foreign-keys to `identity.identities`, because
the migration that breaks that rule will not be this one — it will be
some other table's, months from now, adding a reference that looks
entirely ordinary.

## Rollback

```sql
drop table identity.identities;
```

Then delete the migration, the diagnostic and the test, and remove `0025`
from `supabase_migrations.schema_migrations` in any environment it
reached.

**No data is lost.** The table is empty and nothing references it —
which check 2 verifies rather than assumes.

## Findings

**1 · The roadmap's migration numbers for this epic are wrong, by two.**

§13 names `supabase/migrations/0023_identity.sql`. `0023` and `0024` are
Epic 01's emission helper and consumer cursors — two migrations §12 did
not list, both necessary and both recorded as deviations at the time.
This package is therefore `0025`, and **every later package in §13 shifts
by two**. Recorded in the epic README so the next session does not
rediscover it.

**2 · The backfill is scheduled before the generator it needs.**

WP 02.02 backfills an identity per existing profile. Every row needs a
`person_ref`, which is UUIDv7 and application-generated (§3) — and this
migration deliberately gives the column no default, because
`gen_random_uuid()` would be wrong on both counts and a default is the
kind of convenience that quietly becomes the way rows are made.

**WP 02.03 is what adds UUIDv7 generation, and it comes after 02.02.** So
02.02 has no generator to call. Either it generates v7 values in SQL, or
02.03 moves ahead of it. **Not decided here** — raised for 02.02's
session, which is where the read of the two packages together belongs.

**3 · A structural test that searched raw SQL found its own
documentation.**

The no-foreign-key assertion failed on first run — not on the DDL, but on
the `comment on column` body explaining *why there is no foreign key*.
The test now strips string literals as well as line comments, so it
matches executable DDL only.

Worth recording because it is the same shape of defect as Epic 01's
ambiguous array append: **the test was correct about the rule and wrong
about where to look.** It also means the equivalent negative assertions
in `events.test.js`, `audit.test.js` and `consumerCursors.test.js` carry
the same latent trap — they pass today because no comment in those files
happens to contain the words they forbid. **Not changed here** (they are
Epic 01's, and this package touches no unrelated module); raised so it is
a known trap rather than a future afternoon.

**4 · The locale constraint is duplicated, deliberately and
temporarily.**

`identity.identities.locale` carries the same ten-value check as
`public.profiles.locale`. Adding a locale now means changing two
constraints until step 6 retires `profiles` — real duplication, accepted
because WP 02.06 makes this row authoritative, and an authoritative row
cannot depend on a constraint living on the table it replaces. The
alternative — no constraint until the switch — would let the backfill
introduce values the application cannot render.

## Notes

**`erased_at` is included although erasure is 02.07's package.** §11.4
says erasure *redacts* the row and the reference "remains valid as a key
and resolves to nothing" — without a marker, a redacted row is
indistinguishable from a sparse one and "resolves to nothing" becomes
unanswerable. The column is the structure that statement requires, not a
guess at 02.07's design; the redaction path itself is entirely 02.07's.

**`DELETE` is withheld from every role, including the identity engine.**
§8: an identity is "ended only by erasure, never by inactivity." There is
no correct reason for a row to leave this table, so no role is given the
ability to make one.

**No index beyond the two constraints.** The primary key serves
resolution by person reference — §6.1's hot path, "consulted per request"
— and the unique constraint on `auth_user_id` serves sign-in. There is no
third query yet.
