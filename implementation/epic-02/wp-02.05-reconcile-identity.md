## Tests

**The reconciliation is itself the test**, per roadmap §13. Six checks:

| Check | What it catches | Severity |
|---|---|---|
| 0 | **Nothing to compare** | Fatal — see below |
| 1 | A profile with no identity | Fatal — a name would vanish from a screen |
| 2 | An auth user with two identities | Fatal |
| 3 | Attributes that disagree, across all six fields 02.06 will read | Fatal — a name would change on a screen |
| 4 | A person reference that is missing, not v7, or shared | Fatal |
| 5 | A creation time not carried across | Fatal — the identifier's embedded timestamp would be fiction |
| 6 | An identity with no profile | **Informational** — §11.4's design working |

**Check 0 is the one that matters most and is the least obvious.** An
empty database produces zero discrepancies, and zero discrepancies reads
exactly like success. Without it, the gate is cleared by running it
somewhere with no data — which is precisely the environment available
today.

`reconcileIdentity.test.js` — seven assertions, all about **the ways a
gate breaks by passing**: the refusal exists and comes first; comparison
is null-safe; all six attributes are compared; erased rows are excluded;
an orphan identity is informational; it writes nothing; it raises rather
than only reporting.

## Acceptance criteria

From roadmap §13: *"Zero discrepancies against production data. **A
non-zero result blocks 02.06.**"*

- [x] The reconciliation exists, is read-only, and fails the run on any
      discrepancy
- [x] It detects every class of drift — proven against real rows
- [x] It refuses to report success when there is nothing to compare
- [ ] **Zero discrepancies against production data — NOT MET, and cannot

## Findings

**1 · The reconciliation cannot be `scripts/reconcile/identity.js`, for
the fourth time and the same reason.**

§13 specifies a Node script. It cannot read `identity.identities`:
PostgREST does not expose the `identity` schema and must not, and this
repository has no direct Postgres client. That is the same structural
fact that moved WP 01.06's emission helper into SQL, kept WP 01.07's
consumer store behind an injected port, and put WP 02.04's dual-write in
a trigger.

**This is now a pattern rather than four incidents.** The roadmap was
written assuming application code can reach the new schemas. It cannot,
by a decision Epic 01 made deliberately and verifies continuously.
**Every remaining package that names a file under `scripts/` or `api/`
for work against a non-`public` schema should be read with that in
mind** — starting with 02.06, whose file list is `src/lib/auth.jsx` and
`src/profile/*`.

**2 · The acceptance criterion cannot be met in any environment that
exists, and it blocks 02.06.**

*"Zero discrepancies against production data."*

- **Production has none of this schema.** Migrations `0018`–`0027` have
  never been applied there, and its migration ledger is still
  unreconciled (`ENVIRONMENTS.md` §9), which is a prerequisite for any
  push to it. There is nothing to reconcile.
- **Staging has no data.** Zero auth users, zero profiles. The accounts
  `ENVIRONMENTS.md` §4.4 calls for were never seeded, although Epic 00's
  completion record lists them among what was verified.

So the gate is real, it works, and **it currently has nothing to stand
on**. Roadmap §8 is unambiguous — a read-switch without a passing
reconciliation is not permitted — so **WP 02.06 is blocked**, and this
package's honest outcome is to say so rather than to run the gate
somewhere empty and call it green.

**Two ways to unblock it**, neither of which belongs to this package:

1. **Seed staging** (`ENVIRONMENTS.md` §4.4). Restores a WP 00.06
   obligation, makes this and every later backfill verifiable, and is the
   cheaper path. The accounts must be real enough to sign in with, or
   they are fixtures rather than data.
2. **Reconcile production's ledger and apply `0018`–`0027` there**
   (`ENVIRONMENTS.md` §9). This is what the criterion literally asks for,
   and it puts the epic's schema in front of real users — which is a
   founder decision, not an implementation one, and would want the two
   `Proposed` ADRs accepted first.

**3 · An identity without a profile is correct, and a naive
reconciliation would fail on it.**

`public.profiles` foreign-keys to `auth.users` with `on delete cascade`;
`identity.identities` deliberately has no foreign key at all (WP 02.01).
So deleting an auth user removes the profile and leaves the identity —
which is §11.4 working exactly as designed: *"losing authentication is
not losing identity."*

The obvious symmetric check — every identity has a profile — would fail
on a correct database, and a gate that cries wolf gets waved through.
Check 6 reports the count and passes.

**4 · Erased identities had to be excluded, or erasure reads as drift.**

An erased identity holds no personal data by constraint. Compared against
a profile that still has a name, every erased person would appear as six
mismatched attributes. Check 3 excludes `erased_at is not null`, and the
probe confirms an erased row passes. This is the third package in a row
where erasure — which does not exist yet — had to be accounted for
(02.01's constraint, 02.04's mirror guard, this exclusion).

## Notes

**`is distinct from` throughout, never `<>`.** With nullable columns on
both sides, `<>` yields unknown when either side is null, the row is not
selected, and a real disagreement passes silently. It is the classic way
a reconciliation lies, and the structural test pins it.

**The reconciliation repairs nothing.** When check 1 fires it names the
fix — re-run the idempotent backfill — rather than performing it. A
reconciliation that fixes what it finds cannot also be evidence that
nothing needed fixing.

**Failures name up to ten examples**, not just a count, because the first
question on a non-zero result is always "which ones".
