## ADR required?

**Yes, and one was written first:**
[ADR-0021](../../docs/adr/0021-one-audit-table-with-nullable-workspace.md).

`DATABASE_ARCHITECTURE.md` §33 states audit's isolation as *"Workspace-
scoped, with platform-level administrative actions in a platform-scoped
audit domain."* **"Domain" is genuinely ambiguous between a column value
and a separate table**, the two readings produce different schemas, and
converting between them afterwards is expensive. WP 01.05 cannot avoid
answering it.

The ADR is `Proposed` on the same terms as ADR-0020 — implemented against
an empty table, where changing it is `drop table` and a re-run. That
window closes when the first audit record is written, which is the epic
that builds the write path, not this one.

## Scope

**In scope**

- `platform.audit_outcome` enum; `platform.audit_records` with the twelve
  columns ADR-0021 declares.
- Range partitions for 2026–2027 plus a default.
- The three indexes §10 names for audit.
- Append-only: guard trigger plus withheld privileges, including
  **revoking the INSERT that 0019's default privileges granted**.
- RLS enabled, with the operator read policy.
- `supabase/diagnostics/VERIFY_AUDIT.sql`.

**Explicitly out of scope**

- **The privileged audit write path.** Epic 01's definition lists it
  under Backend, but no work package covers it — raised as a finding
  rather than absorbed here. See Findings 1.
- **The workspace-administrator read policy.** It needs membership, which
  arrives in Epic 03. The operator half of §8 is implemented now so that
  "administrators can read" is true rather than pending.
- Retention by jurisdiction (§33's future expansion).

## Impact

**Database.** Additive. One migration, `0022_audit.sql`: one enum, one
range-partitioned table, three partitions, three indexes, one guard
function and trigger, RLS with one policy, grants and revokes.

**Backend.** None. **Frontend.** None.

**Behaviour.** None — this package is behaviour-preserving. No
application code refers to `platform.audit_records`, and no role that the
application uses can reach it.

## Tests

`supabase/migrations/__tests__/audit.test.js` — eleven structural
assertions, reading the column set out of ADR-0021 rather than restating
it, the same technique 01.04 uses against ADR-0019.

The two that carry the most weight:

| Test | What it protects |
|---|---|
| Grants no role the ability to write, and takes back the engine's insert | §8's central property, which is **one ordinary-looking `grant` away from being untrue**. 0019's default privileges hand the owning engine INSERT on everything created in `platform`; 0022 revokes it, and a future migration re-granting it would look like housekeeping |
| Leaves `workspace_id` nullable and everything identifying NOT NULL | Both directions of ADR-0021. NOT NULL leaves platform-scoped actions with nowhere to go; a second nullable column would make null mean "not recorded" |

Plus: range-partitioned and not hash-partitioned; append-only trigger
present; RLS enabled **with** a policy (deliberately unlike
`platform.events`); nothing granted to the client-facing roles; the
event stream's `actor_type` reused rather than a second enum declared; no
foreign keys; everything guarded.

`supabase/diagnostics/VERIFY_AUDIT.sql` — six checks against a real
database:

| Check | What it proves |
|---|---|
| 1 | Twelve columns; `workspace_id` nullable by decision, the rest not |
| 2 | Range-partitioned by time, three partitions |
| 3 | Writable by nobody — including the owning engine — readable by the operator, RLS on with its policy |
| 4 | **Both scopes land in one table, a denied attempt is recorded, and neither can then be changed** |
| 5 | Malformed actions, anonymous actors and unknown outcomes are refused |
| 6 | Default partition empty; this year and next have ranges |

Check 4 is the one that exercises ADR-0021 directly: it writes a
workspace-scoped record, a platform-scoped one with a null workspace, and
a denied attempt sharing one `correlation_id`, then asks the single
question the two-table reading would have made a `UNION`.

## Acceptance criteria

From roadmap §12: *"Exists; range-partitioned; no application role can
write or update; administrators can read."*

- [x] Exists — `platform.audit_records`, twelve columns
- [x] Range-partitioned — by `occurred_at`, three partitions, no hash
      dimension
- [x] No application role can write — `anon`, `authenticated`,
      `service_role`, all four consumer roles, the operator **and the
      owning engine** all lack INSERT, verified by query
- [x] No application role can update — no UPDATE or DELETE grant exists,
      and the guard trigger refuses both regardless
- [x] Administrators can read — `klussie_operator` holds SELECT and the
      `audit_records_operator_read` policy admits it
- [x] Re-runnable — the whole file re-applied by hand, exit 0

## Rollback

```sql
drop table platform.audit_records;      -- takes its three partitions with it
drop function platform.audit_reject_mutation();
drop type platform.audit_outcome;
```

`platform.actor_type` is **not** dropped — `platform.events` uses it.

Then delete the migration, the diagnostic and the test, and remove `0022`
from `supabase_migrations.schema_migrations` in any environment it
reached. ADR-0021 would be superseded rather than deleted.

**No data is lost.** Nothing writes to this table.

## Findings

**1 · Epic 01's definition lists an audit write path that no work package
builds. Raised, not absorbed.**

The epic definition's Backend paragraph reads: *"Event emission helper
usable inside a transaction. Cursor-based consumer scaffolding. **Audit
write path.**"* The first is WP 01.06 and the second is WP 01.07. **The
third is allocated to nothing.** WP 01.05's acceptance covers the table
and its access posture and stops there, which is what this package
implemented.

This is a real gap rather than a wording quibble, because §8 requires
audit rows to arrive *"through a privileged path"* and no application
role can write the table — so **as things stand, after Epic 01 closes,
nothing can write an audit record at all.** Nothing needs to yet, which
is why this is a finding and not a blocker.

Recommendation: a WP 01.08, or fold it into 01.06 alongside the event
emission helper, which is the same shape of object — a `SECURITY DEFINER`
function owned by a role that can write, callable by engines that cannot.
**Not decided here.**

**2 · The dangerous grant on this table is one 0019 already made.**

`alter default privileges … grant select, insert on tables to
klussie_engine_platform` was the right call in WP 01.02 — it is what
makes engine ownership hold for tables that do not exist yet. On this one
table it is exactly wrong, and the failure is silent: create the table,
and the owning engine can write its own audit trail with no statement
anywhere saying so.

So the migration's `revoke insert` is not tidying — it is the line that
makes §8 true, and the structural test names it specifically for that
reason. **A default that is right nearly everywhere still has to be
checked at every exception**, and this is the first exception in the
schema.

**3 · The `outcome` column is what makes audit irreducible to the event
stream, and it is the only column that says so structurally.**

§33 gives three reasons audit is not derived from events, and two of them
— independent trustworthiness, different retention — are properties of
how the table is used. The first is a property of what it contains: a
denied access attempt produces **no domain event to derive from**. Check
4 writes one, precisely so that the reason is exercised rather than
merely written down.

**4 · The append-only guard protects against the reader with the most
motive.**

On `platform.events` the guard's value showed up as blocking maintenance
by the owner (WP 01.04, finding 1). Here it is sharper: the operator is
the role that can read the whole trail, and an audit trail its most
privileged reader can quietly edit is not a trail. Probe B's failure
message — *"A denied attempt was rewritten as permitted"* — is the actual
threat model, so the diagnostic states it that way rather than as
"UPDATE succeeded".

## Notes

**`platform.actor_type` is reused, not redeclared.** §33 requires every
intelligence action *"marked as machine-originated"*, and
`actor_type = 'intelligence'` **is** that marking. A separate boolean, or
a second enum, would be two places to get one fact right — and the two
tables would drift the first time a fifth actor kind is added.

**The workspace index is partial**, excluding platform-scoped rows. It
answers the tenant question, and platform-scoped records are by
definition not part of any tenant's answer.

**`correlation_id` is shared with ADR-0019's envelope** deliberately, so
an audit record and the events of the same action form one trace. Check 4
relies on it.
