# WP 01.07 — Add cursor-based consumer scaffolding

**Epic.** 01 — Schema Foundation & Event Backbone
**Status.** In review
**Branch.** `epic-01/wp-01.01-ten-schemas`
**Complexity.** High

---

## Goal

A consumer can read forward, record its position, and resume.

## Migration step

**Step 1 — `add`** (roadmap §3). No consumer is wired to anything real.

## Architecture references

- `SUPABASE_ARCHITECTURE.md` §13 — consumers read forward with a cursor,
  record position **per partition**, delivery is at-least-once, every
  consumer is idempotent; a poisoned event is *"quarantined with its
  position recorded, so one bad event never halts a stream
  indefinitely; the quarantine is an operational alert rather than a
  silent skip."*
- `SUPABASE_ARCHITECTURE.md` §12 — the consumer cursor is
  `(occurred_at, event_id)`, with the UUIDv7 supplying the tiebreak.
- `SUPABASE_ARCHITECTURE.md` §9 — background consumers are not one role.
- `SUPABASE_ARCHITECTURE.md` §4 — mutability classes; these are the first
  **Mutable** tables in `platform`.
- [ADR-0019](../../docs/adr/0019-canonical-platform-event-envelope.md) —
  `event_id` is *"the idempotency key every consumer deduplicates on"*.
- [ADR-0020](../../docs/adr/0020-events-partitioning-parameters.md) — the
  modulus that bounds `partition_index`.

## ADR required?

**No.** Every decision is already recorded: cursors per partition,
at-least-once, idempotent consumers, quarantine-not-halt, and the cursor's
shape are all §13 and §12. The only judgement calls — saving the cursor
per event rather than per batch, and `maxBatches` as a stop — are local,
reversible, and stated in the module.

## Scope

**In scope**

- `platform.consumer_cursors` and `platform.consumer_quarantine`.
- Grants: the four consumer roles read, write and **advance**; nobody
  deletes; the operator watches the quarantine.
- `api/_lib/consumers/runner.js` — `runConsumerBatch`, `drainPartition`.
- `supabase/diagnostics/VERIFY_CONSUMERS.sql`.

**Explicitly out of scope**

- **A Postgres store adapter.** There is no application-code path into
  `platform` and there must not be one through PostgREST — see
  Findings 1. The runner takes its store as an argument.
- **Wiring any consumer.** The roadmap says so outright: *"No consumer is
  wired to anything real yet."*
- **`SELECT` on `platform.events` for the three consumers that lack it.**
  Granted by the epic that builds each consumer and knows what it reads.
  The scaffolding needs somewhere to keep a position; it does not need
  the stream.
- **Replay tooling.** Epic 01's stated future extension.

## Tests

**`api/_lib/consumers/__tests__/runner.test.js`, 13 assertions.** The
store double mirrors migration 0024's tables, including the part easiest
to get wrong in a real adapter: `readForward` compares
`(occurred_at, event_id)` as a row, not `occurred_at` alone.

The four that carry the acceptance:

| Test | What it proves |
|---|---|
| Resumes from the cursor with no gap after stopping mid-stream | **Acceptance 1.** The stop is simulated the way it happens: the process is gone and only what reached the store survives |
| Redelivers at most the one event a crash straddled | Pins the size of the at-least-once window — one event, not one batch |
| Produces no duplicated effect when the handler is idempotent | The half of "no duplicated effect" that is **not this module's to give**; §13 requires the handler to deduplicate on `event_id` |
| Quarantines a poisoned event and keeps going | **Acceptance 2.** Plus: the cursor advances past it, because leaving it behind is the halted stream §13 forbids |

Plus: cursors independent per partition and per consumer; events sharing
a timestamp delivered exactly once each; `exhausted` accurate;
`maxBatches` bounded; a missing handler refused.

**`supabase/migrations/__tests__/consumerCursors.test.js`, 10
assertions.** Chiefly guarding against the reflex this schema teaches —
every other table in `platform` is append-only, so "add the guard, withhold
UPDATE" is the wrong instinct here and applying it breaks a consumer
silently: the cursor stops advancing and the consumer looks healthy while
reprocessing its first batch forever.

**`supabase/diagnostics/VERIFY_CONSUMERS.sql`, 5 checks** against the real
tables: both exist and neither is guarded; consumers can advance and
nobody can delete; partial positions, impossible partitions and duplicate
cursors are refused; a cursor advances and re-quarantining counts
attempts; nothing is currently quarantined.

## Findings

**1 · There is still no application-code path into `platform`, and this
package is where that stops being theoretical.**

WP 01.06 raised it; a consumer is the first thing that genuinely needs
it. PostgREST does not expose the `platform` schema and **must not** —
§12 makes the events table not client-readable, so exposing the schema to
reach a cursor would expose the stream to reach it too. A real consumer
therefore needs a **direct Postgres connection**, which this repository
does not have: there is no `pg` client dependency, and adding one is a
tooling decision belonging to the epic that runs the first consumer, not
to a scaffolding package.

So the runner takes its store as an argument. That is not a test
convenience dressed up as design — it is the only honest shape while the
transport is undecided, and it is what lets the resumption and quarantine
behaviour be proven now rather than asserted. **The storage is real as of
0024; the adapter is a named, deliberate gap.**

**2 · Saving the cursor after the handler is the choice that cannot be
reversed later without changing what "at-least-once" means.**

Both orderings lose something. Save first, and a crash between saving and
handling **skips an event entirely** — no retry recovers it, and nothing
detects it, because the cursor says the work was done. Save after, and a
crash redelivers one event that was already handled.

Only the second failure is recoverable, and §13 already requires every
consumer to be idempotent, which makes redelivery a non-event. Probe B
demonstrated the difference: reversing the order turns the redelivery
test into a silent skip.

Worth stating plainly because the reversed order **looks more efficient**
and passes twelve of the thirteen tests.

**3 · These are the first mutable tables in `platform`, and the schema's
own conventions work against them.**

Every other table here is append-only with a guard trigger and no UPDATE
grant. Applying that reflex to a cursor produces a consumer that cannot
advance — and it fails *silently*, because at-least-once delivery means
reprocessing the same batch forever looks exactly like a healthy consumer
with a quiet stream.

This is the case `ROLES.md` §3 rule 2 anticipated: the default is right
nearly everywhere and has to be checked at every exception. The migration
names the mutability class in a comment block, the structural test asserts
that no guard trigger exists, and the diagnostic checks for one. Three
places, because the reflex is strong and the failure is invisible.

**4 · `DELETE` is withheld from everyone, including the consumers.**

A consumer deleting its own cursor is not obviously wrong — it reads like
a reset. It is: the consumer silently restarts from the beginning of a
partition, reprocesses everything, and because handlers are idempotent,
**nothing observable happens** except load. Withholding `DELETE` makes the
reset an explicit administrative act rather than something a retry loop
can do by accident.

## Notes

**A migration was added that the roadmap's file list does not mention**,
for the same reason as WP 01.06: the roadmap names `api/_lib/consumers/`
alone, and a cursor that is not durable is not a cursor. Stated rather
than buried.

**`maxBatches` is a stop, not a tuning knob.** An unbounded drain over a
stream still being written to never returns. A caller that wants to keep
going calls again.

**The quarantine catch is deliberately broad.** §13's rule is that one
bad event never halts a stream indefinitely, and a handler fails for
reasons this module cannot enumerate. Distinguishing "retryable" from
"poisoned" here would be guessing; the reason is recorded and an operator
decides.

**Check 5 of the diagnostic is operational, not acceptance.** It reports
open quarantines, and it passes today because nothing consumes anything.
It is the check that will matter most once something does.
