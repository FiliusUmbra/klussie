# WP 01.03 — Install extensions in a dedicated schema

**Epic.** 01 — Schema Foundation & Event Backbone
**Status.** In review
**Branch.** `epic-01/wp-01.01-ten-schemas`
**Complexity.** Low

---

## Goal

`ltree` and `pg_cron` are available, and nothing is in `public`.

## Migration step

**Step 1 — `add`** (roadmap §3). Two extensions, no objects, no grants.

## Architecture references

- `SUPABASE_ARCHITECTURE.md` §2 — *"Extensions live in their own schema
  and are never installed into `public`."* The one rule this package has
  to satisfy.
- `SUPABASE_ARCHITECTURE.md` §11.2 — `ltree` is the chosen materialised
  path for the location tree: containment becomes a prefix match on an
  indexed path rather than a recursive walk per query.
- `SUPABASE_ARCHITECTURE.md` §18 — cron owns due-date evaluation,
  document expiry, workflow timers, retention sweeps, archival and
  projection health. Explicitly **not** event delivery, which is
  cursor-driven.

## ADR required?

**No.** Both extensions and their placement rule are already chosen in
frozen documents. The one judgement here — using Supabase's existing
`extensions` schema rather than creating one — is the "extend before
rewriting" default (roadmap §4 rule 7) applied to a question the platform
has already answered, and is reversible by one migration.

## Scope

**In scope**

- `ltree` in `extensions`.
- `pg_cron`, wherever PostgreSQL insists on putting it.
- `supabase/diagnostics/VERIFY_EXTENSIONS.sql`.

**Explicitly out of scope**

- **Any grant.** Nothing runs as an engine role yet;
  `docs/operations/ROLES.md` §3 rule 1 says a privilege is granted when a
  real query needs it. Epic 06 grants `usage on schema extensions` to
  `klussie_engine_property` when it creates the first `ltree` column.
- **Any scheduled job.** §18 gives cron real work; none of it exists.
- Any other extension.

## Impact

**Database.** Additive. One migration, `0020_extensions.sql`. Two
extensions; `pg_cron` brings a `cron` schema of its own with seven
objects. No table, no grant, no job, nothing in `public`.

**Backend.** None. **Frontend.** None.

**Behaviour.** None — this package is behaviour-preserving. Neither
extension is referenced by any application code, and `pg_cron` with no
scheduled jobs runs nothing.

| Test | Type | What it proves |

added. An extension enabled from the Supabase dashboard defaults to

## Rollback

```sql
drop extension ltree;
drop extension pg_cron;   -- also drops the cron schema it created
```

Then delete the migration, the diagnostic and the test, and remove `0020`
from `supabase_migrations.schema_migrations` in any environment it
reached. **No data is lost** — nothing uses either extension.

## Findings

**1 · `pg_cron` is not relocatable, and says so by ignoring you rather
than by failing.**

`create extension pg_cron with schema extensions` **succeeds**. It then
registers the extension in `pg_catalog` and creates a `cron` schema for
its seven objects, exactly as if the clause had not been written. Probed
in a rolled-back transaction before the migration was written:

| Statement | Extension lands in |
|---|---|
| `create extension pg_cron` | `pg_catalog` |
| `create extension pg_cron with schema extensions` | `pg_catalog` |

So the migration omits the clause. Writing it would have left a line that
appears to make a decision, makes none, and would be read by the next
person as evidence that placement was under our control here. It is not,
and `VERIFY_EXTENSIONS.sql` deliberately does not assert a schema for
`pg_cron` — asserting something PostgreSQL decides is a test that fails
for reasons no one can act on.

**This is not a conflict with §2 and does not need an ADR.** The rule §2
states is that extensions are never installed into `public`. Nothing
lands in `public`; `pg_cron` has its own schema in the ordinary sense,
just not one we chose.

**2 · Supabase already provides an `extensions` schema, and it is not one
of §2's ten.**

`pgcrypto`, `uuid-ossp` and `pg_stat_statements` were already there on a
freshly migrated staging project. §2 says extensions live in "their own
schema" without naming it — so the choice is between using the platform's
and creating an eleventh of our own. Using the existing one is roadmap §4
rule 7 applied directly, and it keeps the ten-schema list in §2 exactly
what the frozen document says it is.

**3 · An `ltree` column will need explicit qualification.**

`extensions` is not on the search path a migration runs under, so the
first Location migration (Epic 06) declares its column as
`extensions.ltree` and its index as `using gist (path extensions.gist_ltree_ops)`.
Recorded here because the failure mode is a confusing `type "ltree" does
not exist` in a migration whose author has just verified the extension is
installed. Qualifying is the right habit regardless: a type resolved
through `search_path` is a type that can resolve differently later.

**4 · `anon` and `authenticated` already hold `USAGE` on `extensions`.**

Supabase grants this by default; it predates this package and is not
changed by it. Worth recording because `ROLES.md` §2.4 says this platform
grants those roles nothing — that statement is about the ten schemas, and
`extensions` is Supabase's, governed by Supabase's defaults. No engine
role holds it, which is the part this epic controls.

## Notes

**Both extensions are installed several epics before they are used.**
That is deliberate: it makes the first migration that creates an `ltree`
column a schema change rather than a schema change *and* an infrastructure
change, and it means the question "is cron available on this plan" is
answered now rather than during the epic that depends on the answer.
