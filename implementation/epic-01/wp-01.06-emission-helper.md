# WP 01.06 — Add the transactional event emission helper

**Epic.** 01 — Schema Foundation & Event Backbone
**Status.** In review
**Branch.** `epic-01/wp-01.01-ten-schemas`
**Complexity.** Medium

---

## Goal

An engine can emit an event inside its own transaction.

## Migration step

**Step 1 — `add`** (roadmap §3). Nothing calls it. The legacy
`emit_domain_event` path is untouched.

## Architecture references

- `SUPABASE_ARCHITECTURE.md` §12 — constraint 5: events written in the
  same transaction as the change, so a change without an event is
  impossible.
- `SYSTEM_ARCHITECTURE.md` §5 — *"the transaction ends at the event"*;
  `correlation_id` is *"propagated, never regenerated"*; the Event
  Backbone is a shared contract every engine uses, not an engine.
- [ADR-0019](../../docs/adr/0019-canonical-platform-event-envelope.md) —
  `subject_sequence` is gapless, engine-assigned, and **not** enforceable
  by a database constraint here; reusing ADR-0004's signature is ruled
  out.
- `SUPABASE_ARCHITECTURE.md` §3 — identifiers are application-generated.
- `SUPABASE_ARCHITECTURE.md` §9 — an engine has no write access to
  another engine's schema.

## ADR required?

**No.** Every decision here is already recorded. That emission is
transactional is constraint 5; that the sequence is gapless and
serialises writes to one subject is ADR-0019, which also states the
trade explicitly. The advisory lock is *how* that serialisation is
achieved, not *whether* — a mechanism with no real alternative, since
without it the field does not mean what the ADR says it means.

## Scope

**In scope**

- `platform.emit_event(...)` — `SECURITY DEFINER`, assigns the next
  gapless `subject_sequence`, inserts into `platform.events`, returns the
  sequence.
- `EXECUTE` revoked from `PUBLIC`, granted to the seven engine roles.
- `buildEventEnvelope()` in `api/_lib/events.js` — the JS side of
  ADR-0019's contract.
- `supabase/diagnostics/VERIFY_EMISSION.sql`.

**Explicitly out of scope**

- **A JavaScript function that emits.** It would get its own transaction
  — an event with no change attached, which is the shape constraint 5
  forbids. See Findings 1.
- **UUIDv7 generation.** WP 02.03. Callers supply identifiers, per §3.
- **Wiring any real emitter.** No engine exists.
- **Granting emission to consumers.** Derived events are real (ADR-0019)
  but no consumer emits one yet; `ROLES.md` §3 rule 1.
- **`public.domain_events`.** Untouched, still live.

## Impact

**Database.** Additive. One function, one revoke, seven grants.

**Backend.** `api/_lib/events.js` gains two exports. The existing

## Tests

**JS — `api/_lib/__tests__/events.test.js`, 12 assertions.** Less about
"does it work" than about pinning the rules a caller in a hurry would
route around: supplying a sequence, omitting a correlation id, passing a
truthy string for `isDerived`.

**SQL structure — `supabase/migrations/__tests__/emitEvent.test.js`,
7 assertions.** Two pin things that are invisible when broken:

| Test | What it protects |
|---|---|
| Serialises per subject with a transaction-scoped advisory lock | **Remove the lock and everything still passes** — every event gets a sequence, nothing looks wrong, until two concurrent writes to one subject take the same number. ADR-0019 says no constraint can catch that here |
| Requires an event id and correlation id with no default | A default looks like ergonomics and silently starts a new trace whenever a caller forgets |

Plus: `SECURITY DEFINER` with an empty `search_path`; `EXECUTE` revoked
from `PUBLIC` **before** being granted; seven engine roles and no
consumer or client role; the legacy path not mentioned.

**SQL behaviour — `supabase/diagnostics/VERIFY_EMISSION.sql`, 5 checks.**

| Check | What it proves |
|---|---|
| 1 | **An event emitted in a rolled-back transaction does not exist** — and is visible inside its own transaction first, which is what makes it usable by an engine mid-change |
| 2 | **An event emitted in a committed transaction does exist**; one subject sequences 1, 2; a second subject starts again at 1; the sequence persists across transactions |
| 3 | Missing identifiers and malformed types are refused, not defaulted |
| 4 | `SECURITY DEFINER`, executable by the seven engines and nobody else |
| 5 | `public.domain_events` and its RPC are untouched |

Check 2 is **the only place in this repository that deliberately
commits**, because "a committed event survives" cannot be observed from
inside the transaction that wrote it. It cleans up by suspending the
append-only guard for one session — the only way to remove a row from
that table, and itself evidence the guard works.

## Findings

**1 · The helper cannot be JavaScript, and that is the finding rather
than an inconvenience.**

The roadmap's file list for this package is `api/_lib/events.js` alone,
which reads as though the helper is a JS function. It cannot be.
Constraint 5 requires the event and the change to share a transaction; a
helper invoked over RPC gets its own, so an event emitted that way is an
event with no change attached — the exact shape the constraint forbids.
`SYSTEM_ARCHITECTURE.md` §5 says the same thing from the other side:
*"the transaction ends at the event."*

So the transactional guarantee is `platform.emit_event()`, called by an
engine from inside its own transaction, and the JS module's contribution
is the envelope those callers pass in. **A migration was added that the
roadmap's file list does not mention**, which is a deviation worth
stating plainly rather than burying.

**A consequence worth carrying forward:** there is deliberately **no
application-code path to `platform.emit_event`**. PostgREST does not
expose the `platform` schema and must not — §12 makes the events table
not client-readable, and exposing the schema to reach the function would
expose the table to reach it too. Engines will call it SQL-side. If a JS
caller is ever genuinely needed — a consumer emitting a derived event,
where the event *is* the whole write — it needs a direct Postgres
connection, which this repository does not currently have. **Raised for
WP 01.07**, which is the first package likely to want one.

**2 · Gaplessness needed a lock, and the lock is the kind of line
somebody tidies away.**

ADR-0019 requires `subject_sequence` to be gapless and says outright that
PostgreSQL cannot enforce it here. Deriving it as `max + 1` without
serialising is a plain read-then-insert race: two concurrent transactions
read the same maximum and write the same sequence, and **nothing rejects
it** — there is no unique constraint, by the ADR's own reasoning.

`pg_advisory_xact_lock` on `(workspace, subject_type, subject_id)` is the
mechanism. Transaction-scoped deliberately: it releases on commit *and*
on rollback, with no unlock path to forget. The contention is per
subject, which is the trade ADR-0019 chose over a per-workspace ordering
point that would have made the platform's largest customers its slowest.

It is pinned by a test because it is invisible when removed — every
existing check still passes without it.

**3 · A latent defect in two already-committed diagnostics, found by a
probe rather than by review.**

Probing check 3 produced `ERROR: malformed array literal` instead of the
intended message. The cause: `some_text_array || 'a literal'` is
ambiguous in PostgreSQL, which can resolve it as `array || array` and try
to parse the string as an array literal.

The same construct is in **`VERIFY_EVENTS.sql` and `VERIFY_AUDIT.sql`,
committed in WP 01.04 and 01.05** — on paths no probe had taken, because
those probes exercised the `format(...)` branches, which are explicitly
typed and resolve correctly. Both files are fixed here (19 casts to
`::text`), and both re-verified.

**The gates never actually failed open** — a wrong grant or a missing
guard still exited non-zero, which is what the checks are for. What was
broken was the message, on exactly the paths someone would be reading
under pressure. Worth recording because the lesson generalises: **a probe
that only exercises one branch of a check has only verified that branch**,
and the branches these files take on failure are the ones nobody runs
until something is wrong.

**4 · `coalesce` cannot be schema-qualified.**

`set search_path = ''` on a `SECURITY DEFINER` function means every
function reference must be qualified — but `coalesce` is a SQL construct
rather than a function, so `pg_catalog.coalesce(...)` fails with *"function
pg_catalog.coalesce(bigint, integer) does not exist"*. It needs no
qualification because it cannot be shadowed. The migration says so in a
comment, since the natural reaction to the error is to remove the empty
search path rather than the qualification.

## Notes

**The migration was pushed before its diagnostic could run**, because a
diagnostic cannot test a function that does not exist. Finding 4's error
was fixed by re-applying the corrected file by hand; staging now holds
the correct function and the repository holds the correct file, so a
fresh environment replaying migrations gets the right one. Recorded so
that the ledger entry's ordering is not mistaken for a discrepancy.

**`buildEventEnvelope` deliberately does not send.** Shipping a call path
that is known to be unreachable would be dead code (roadmap §4 rule 10);
shipping one that *works* would ship the anti-pattern in finding 1.

**The validation duplicates constraints that also exist on the table.**
Not redundancy for its own sake: a check violation raised inside a
`SECURITY DEFINER` function names a table the caller may not know exists
and says nothing about which argument caused it. These name the field.
