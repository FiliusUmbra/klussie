# WP 01.02 — Establish role grants mirroring engine ownership

**Epic.** 01 — Schema Foundation & Event Backbone
**Status.** In review
**Branch.** `epic-01/wp-01.01-ten-schemas`
**Complexity.** Medium

---

## Goal

Cross-schema writes fail on privileges, not on review.

## Migration step

**Step 1 — `add`** (roadmap §3). Grants and roles only. Nothing existing
is altered; the running application's access to `public` is untouched.

## Architecture references

- `SUPABASE_ARCHITECTURE.md` §9 — the four role classes, "grants mirror
  engine ownership", and "background consumers are not one role".
- `SUPABASE_ARCHITECTURE.md` §24 item 2 — *"an engine writing another
  engine's schema must fail on privileges"*. This package is that
  sentence, executable.
- `SUPABASE_ARCHITECTURE.md` §4 and §24 item 7 — append-only is enforced
  by withholding `UPDATE`/`DELETE`, with the mutability class declared
  per table. Determines what the default privileges may contain.
- `SUPABASE_ARCHITECTURE.md` §7 — the direct-read path is permitted only
  where membership alone is the complete answer, which is why nothing is
  granted to `authenticated` schema-wide.

## ADR required?

**No**, and the roadmap already says where the decision goes: §12 assigns
`docs/operations/ROLES.md` to this package. The role *classes*, their
boundaries and the ownership rule are all frozen in §9; what this package
adds is the concrete role names and the per-table granting discipline,
which is operational detail with a documented home. Nothing here
contradicts a frozen document or would be expensive to reverse — §6 of
`ROLES.md` is a twelve-role drop.

## Scope

**In scope**

- Twelve `NOLOGIN` roles: seven engine, four consumer, one operator.
- `USAGE` per §9's boundaries, and default privileges so a new table is
  readable and insertable by its own engine.
- Explicit revokes for `anon`, `authenticated`, `service_role` and
  `PUBLIC` across all ten schemas.
- `docs/operations/ROLES.md` — the matrix and the five rules later
  migrations follow.
- `supabase/diagnostics/VERIFY_GRANTS.sql` — an executable check of the
  posture.

**Explicitly out of scope**

- **Cross-schema read grants.** §9 permits read-only elsewhere; there is
  not one table to read yet, so granting now would be the opposite of
  "the narrowest grants that let it work". Granted by the epic with a
  real query. Recorded as rule 1 in `ROLES.md` §3.
- **Any table privilege**, since no table exists in the ten schemas.
- **Granting any role to a connection role.** Nothing runs as an engine
  role until an engine has its own connection.
- **RLS.** A separate concern (§6), arriving with the tables it protects.
- Anything in `public`.

## Impact

**Database.** Additive. One migration, `0019_grants.sql`: twelve roles,
schema `USAGE` grants, default privileges, and revokes that are no-ops
today. No table, no policy, no change to `public`.

**Backend.** None. No application code refers to any of these roles.

**Frontend.** None.

**Behaviour.** None — this package is behaviour-preserving. Nothing can
connect as any new role, and the roles the application actually uses
(`anon`, `authenticated`, `service_role`) keep exactly the access to
`public` they had.

## Tests

Two halves, which fail differently and are both needed.

`supabase/migrations/__tests__/grants.test.js` — six structural
assertions over the SQL:

| Test | Type | What it proves |
|---|---|---|
| Names only schemas the frozen architecture declares | unit | A stray or misspelled schema name cannot enter the grant file |
| Each engine role gets usage on its own schema and no other | unit | The mis-pairing this package exists to prevent. `grant usage on schema work to klussie_engine_workspace` is a plausible typo that reads correctly at a glance |
| Never grants update or delete | unit | Append-only stays the default (§4). A default that granted them would make every future append-only table depend on someone remembering to revoke |
| Grants nothing to `anon`, `authenticated`, `service_role`, `public` | unit | §9's permanent rules, and §7's per-table discipline, cannot be relaxed schema-wide by accident |
| Touches nothing in `public`, creates no objects | unit | The package stays within its scope |
| Creates every role guardedly | unit | `create role` has no `if not exists`; re-runnability depends entirely on the guard |

`supabase/diagnostics/VERIFY_GRANTS.sql` — four checks against a real
database, because a grant's effect is not visible in its text:

| Check | What it proves |
|---|---|
| 1 | Twelve roles exist; none can log in — a boundary, not an account |
| 2 | Each engine role reaches its own schema and no other, across all ten |
| 3 | `anon`, `authenticated`, `service_role` reach none of the ten |
| 4 | A table created in a schema is `SELECT`+`INSERT` to its own engine and nothing to anyone else — the only way to see what the default privileges actually did |

Check 4 creates a table inside a transaction and rolls it back, so the
script stays safe to run against any environment.

The structural test was probed in 01.01's manner during development and
fails on a mis-paired engine role, on any `grant … to authenticated`, and
on an unguarded `create role`.

## Rollback

`docs/operations/ROLES.md` §6, in full: revoke the default privileges,
`drop owned by` the twelve roles, then drop them. Delete the migration,
the diagnostic, the two test files and `ROLES.md`, and remove `0019` from
`supabase_migrations.schema_migrations` in any environment it reached.

**No data is lost, in any environment.** Nothing runs as these roles and
no object is owned by one. The §2.4 revokes need no reversing: they
removed nothing, because PostgreSQL grants nothing to `PUBLIC` on a newly
created schema.

## Findings

**1 · Default privileges are the only mechanism that makes engine
ownership hold for tables that do not exist yet — and they carry a
direction of failure.**

Grants apply to existing objects. Every table this platform will ever
have is created by a future migration, so the ownership rule has to be
expressed as `alter default privileges` or it has to be repeated,
correctly, in every migration for the next twenty-five epics. The second
is not a plan.

What the default *contains* then decides which way a mistake falls. A
default of `select, insert` leaves a forgotten table too strict — append
attempts work, updates fail, someone notices. A default that included
`update, delete` leaves a forgotten append-only table silently mutable,
which §4 and §24 item 7 both forbid and neither would detect. The
migration takes the first, and `ROLES.md` §3 rule 2 makes the mutable
case an explicit, per-table opt-in that names its class.

**2 · Three of the ten schemas have no engine role, and that is
correct.**

`derived`, `analytics_ws` and `analytics_pf` are not owned by one engine:
§2 assigns `derived` to *"whichever engine owns each projection"* and the
analytics pair to the Analytics engine, whose work is done by a consumer.
Inventing `klussie_engine_derived` to make the table symmetrical would
have created a role with no owner and a boundary with no meaning. The
asymmetry is the architecture's, and is recorded in `ROLES.md` §2.1
rather than smoothed over.

**3 · `service_role` is not one of §9's service roles.**

Supabase's `service_role` is the elevated role of §7's third access path.
§9's "Service (background)" class is per-consumer and deliberately
plural. The names collide and the concepts do not, which is the specific
reason every role created here is prefixed `klussie_` — `klussie_consumer_*`
cannot be mistaken for `service_role` in a review.

## Notes

**`frozenSchemas.js` was extracted** rather than the parser being copied
into the second test. Two copies would be two places for the ten names to
drift from `SUPABASE_ARCHITECTURE.md` §2, which is the one document
allowed to say what they are. 01.01's test is otherwise unchanged and its
four assertions still pass.

**The revokes in `0019` are no-ops today** and are written anyway. The
posture should be stated where it is enforced; an absence of grants is
indistinguishable from an oversight, and the next person to read the file
should not have to know that PostgreSQL grants nothing to `PUBLIC` on a
new schema in order to know that the omission was deliberate.
