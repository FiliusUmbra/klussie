# WP 01.01 — Create the ten schemas with no tables

**Epic.** 01 — Schema Foundation & Event Backbone
**Status.** In review
**Branch.** `epic-01/wp-01.01-ten-schemas`
**Complexity.** Low

---

## Goal

The ten engine-tier schemas exist; nothing has moved into them.

## Migration step

**Step 1 — `add`** (roadmap §3). Pure addition. Nothing reads or writes
the new structure, and no existing structure is altered.

## Architecture references

- `SUPABASE_ARCHITECTURE.md` §2 — names the ten schemas and what each
  owns. This package creates exactly those, with no additions and no
  renames.
- `SUPABASE_ARCHITECTURE.md` §2 — "`public` itself holds nothing" is the
  *destination*, not this package: `public` is left entirely untouched
  and the running product continues to use it.
- `DATABASE_ARCHITECTURE.md` §31 — why `analytics_ws` and `analytics_pf`
  are two schemas rather than one with a convention.
- `SYSTEM_ARCHITECTURE.md` §1 rule 2 — the rule these boundaries exist to
  let PostgreSQL enforce once 01.02 adds grants.

## ADR required?

**No.** The ten schemas, their names and their contents are already
decided and frozen in `SUPABASE_ARCHITECTURE.md` §2. This package
implements that decision literally and makes no new one. Nothing here is
debatable, pattern-setting, or expensive to reverse — the rollback is
ten `drop schema` statements against empty schemas.

## Scope

**In scope**

- Create the ten schemas named in `SUPABASE_ARCHITECTURE.md` §2.
- A schema comment on each, recording its owning engines.
- A structural test binding the migration to the frozen document.

**Explicitly out of scope**

- **Grants** — WP 01.02. Deliberately not done here: grants are 01.02's
  rollback point, and a schema with no grants is inert in a way a schema
  with the wrong ones is not.
- **Extensions** — WP 01.03.
- **Any table, function, type, view or index** — 01.04 onward.
- **Anything in `public`.** Not narrowed, not prepared, not touched.
- Production. This package is applied to staging only.

## Impact

**Database.** Additive. One migration, `0018_schemas.sql`. Ten empty
schemas, ten schema comments. No table, no grant, no change to `public`.

**Backend.** None.

**Frontend.** None.

**Behaviour.** None — this package is behaviour-preserving. The new
schemas are unreachable by every application role (verified below) and
none is on PostgREST's exposed-schema list, so no client can name one.

## Tests

`supabase/migrations/__tests__/schemas.test.js` — four assertions. There
is no database in the harness (`TESTING.md` §3), so these are structural
tests over the SQL; execution is proven on staging under Verification.

| Test | Type | What it proves |
|---|---|---|
| Reads ten schemas out of the frozen architecture | unit | The parse works. Without it, a formatting change to §2 would leave two empty lists comparing equal and a suite that passes while checking nothing |
| Creates exactly the schemas the architecture names | unit | An eleventh schema, a rename or a merge fails the build. §2 is frozen; changing it is an ADR, not a migration line |
| Creates every schema guardedly | unit | Every `create schema` is the `if not exists` form, so the migration is re-runnable (roadmap §3) |
| Adds nothing to `public` and creates no objects | unit | The package stays inert. A table, a grant or a `public.` reference is a different work package |

**The test derives the ten names from the frozen document rather than
restating them.** A hard-coded list in a test file is a second source of
truth and would be the first thing to drift.

## Rollback

```sql
drop schema identity restrict;
drop schema workspace restrict;
drop schema property restrict;
drop schema work restrict;
drop schema knowledge restrict;
drop schema commerce restrict;
drop schema platform restrict;
drop schema derived restrict;
drop schema analytics_ws restrict;
drop schema analytics_pf restrict;
```

Then delete the migration and its test, and remove `0018` from
`supabase_migrations.schema_migrations` in any environment it reached.

**No data is lost, in any environment.** The schemas are empty by
construction and nothing outside them references them. `restrict` rather
than `cascade` is deliberate: if a later epic has put something in one,
the drop should fail loudly rather than take the contents with it.

## Findings

**1 · Nothing had to be done to make the schemas inert.**

The expectation was that new schemas might need an explicit
`revoke all ... from public` to stop `anon` and `authenticated` reaching
them, since Supabase configures default privileges on `public`. Checked
rather than assumed: `has_schema_privilege` returns false for all three
application roles across all ten schemas with no revoke present.
PostgreSQL grants nothing to `PUBLIC` on a newly created schema, and
Supabase's default-privilege configuration is scoped to `public` itself.

This matters beyond this package: it is why steps 1–4 of the migration
pattern are genuinely inert for every later schema epic, and why 01.02
can be a clean rollback point instead of a correction.

**2 · `identity` and `work` are non-reserved keywords and need no
quoting.**

Both appear in PostgreSQL grammar (`GENERATED ... AS IDENTITY`,
`COMMIT WORK`) and are non-reserved, so they work unquoted as schema
names. Confirmed by applying the migration rather than by reading the
keyword table. Worth recording because quoting one of them "to be safe"
would have made every later reference case-sensitive — a small decision
with a long tail.

## Notes

**Why comments on schemas.** `comment on schema` is metadata with no
runtime effect, and it puts §2's ownership table where a person reading
the database will actually find it. Idempotent, so it does not
compromise re-runnability.

**The migration is grouped by tier with the reasoning inline**, rather
than being ten bare statements. The grouping is not load-bearing — the
statements are independent — but the reasons the boundaries fall where
they do (identity apart from workspace, commerce apart from work, the two
analytics schemas apart from each other) are the part a future reader
will need and the part that is easiest to lose.
