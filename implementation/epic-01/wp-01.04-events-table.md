## ADR required?

**Yes, and one was written first:**
[ADR-0020](../../docs/adr/0020-events-partitioning-parameters.md).

§12 says events are hash-partitioned by workspace *"into a fixed number
of partitions, each range-partitioned by time"* and does not say what
that number is, how wide a range is, or what happens to a row outside
every range. All three meet `adr/README.md`'s tests: the first is awkward
to reverse once the table is large, a future contributor could plausibly
change any of them without knowing why, and all three set the pattern for
the four other tables §19 partitions the same way.

**The ADR is `Proposed`, not `Accepted`, and that is deliberate.** It is
implemented against an empty table in staging. Changing the modulus now
is `drop table` and a re-run; changing it once production events exist is
the expensive operation the ADR exists to make deliberate. **The window
in which this is free closes when the first event is written, which is
Epic 09 at the earliest.** It needs the founder's sign-off before then,
and nothing else in this epic depends on the answer.

## Rollback

```sql
drop table platform.events;          -- takes all 24 partitions with it
drop function platform.events_reject_mutation();
drop type platform.actor_type;
```

Then delete the migration, the diagnostic and the test, and remove `0021`
from `supabase_migrations.schema_migrations` in any environment it
reached. ADR-0020 would be superseded rather than deleted.

**No data is lost.** Nothing writes to this table; the product's events
continue to flow through `public.domain_events`, which this package does
not touch.

## Findings

**1 · The guard trigger is doing work the privileges cannot, and the
cleanup proved it.**

§24 item 7 requires withheld privileges *plus* a guard trigger, and it is
easy to read that as belt-and-braces. It is not. Removing the probe row
from the default partition required
`set session_replication_role = replica` — **the connection was
`postgres`, the table's owner, and it still could not delete a row.**
Privileges stop an application role and stop nothing else; the trigger
stops the superuser doing maintenance at speed, and a background consumer
running with `BYPASSRLS`. The two failure modes do not overlap, which is
why the frozen document asks for both.

Worth knowing operationally as well: **legitimate removal of a row from
this table requires deliberately suspending triggers**, which is exactly
the friction an append-only table should have, and is the same mechanism
[ADR-0018](../../docs/adr/0018-restore-mode-suspend-triggers-during-logical-restore.md)
already anticipated for restores.

**2 · An event written outside every defined range succeeds, which is the
point.**

Probed rather than assumed: an event dated June 2025 inserted cleanly and
landed in `events_w4_default`. Without the default partition that insert
would have raised — and because events are written in the same
transaction as the change they describe, the failure would not have been
"an event was lost", it would have been **a customer's booking failing**,
at midnight on the first of January, when nobody is looking.

The default is a safety net with a rule attached, and check 6 is that
rule: a populated default is a defect to fix, not a place for events to
live. ADR-0020 records both halves.

**3 · The envelope test only earns its keep by reading the ADR.**

The first version of this test restated the thirteen field names. That
version catches a column removed from the migration and is blind to the
opposite and more likely case — the envelope being extended in ADR-0019
while the table is not. Since §12's whole argument is that this table is
never rewritten, the direction that matters is the one a copied list
cannot see. Parsing the ADR was a few lines and makes the failure message
name the actual disagreement.

**4 · `subject_sequence` uniqueness is asserted nowhere, deliberately, and
the migration says so in the file.**

PostgreSQL requires a unique constraint on a partitioned table to include
every partition key column, so a constraint including `occurred_at` would
permit the same sequence twice in two time partitions — precisely what
the field forbids. ADR-0019 records this; the migration repeats it in a
comment block because the person most likely to assume otherwise is
reading the SQL, not the ADR.

## Notes

**The check constraints were chosen against §4's test** — *does this
refuse an impossibility, or make a decision?* All four refuse: an
`event_type` that cannot be dispatched, a non-positive version, a
sequence of zero, and an event that claims to have caused itself. None
encodes a process or chooses anything.

**`events_causation_idx` is partial.** A root event has no parent, so
indexing the nulls would index most of the table for a query that never
asks for them.

**Indexes are created on the parent**, so PostgreSQL propagates them to
partitions that do not exist yet — including the ones created in 2028 by
whoever is on call then.
