## Notes

**Node version pinned to 22 LTS.** `package.json` declares no `engines`
field and the repository has no `.nvmrc`, so CI pins a version explicitly
rather than inheriting a runner default that can change under us. If
local development uses a different major version, that mismatch is worth
knowing and is exactly the kind of thing CI should surface.

**`npm ci` rather than `npm install`.** `package-lock.json` is committed;
`npm ci` installs exactly what it specifies and fails if the lockfile and
manifest disagree. `npm install` would silently update the lockfile in
CI, which makes a green run less meaningful.

**Least-privilege permissions.** The workflow declares `contents: read`.
This is correct workflow authorship rather than scope expansion — the
default token grants more than this job needs.

**"Blocks merge on failure" needs a repository setting, not a file.** The
work package's own criterion is that a failing test *blocks the run*, and
that is met. The *epic* acceptance criterion says CI "blocks merge on
failure", which requires branch protection on GitHub — a repository
administration setting that cannot be created from the repository. This
is flagged as an outstanding item for the Epic 00 completion gate and is
not silently claimed as done here.

**The failing-test check.** Verified locally that a failing test makes
`npm test` exit non-zero, which is the mechanism by which the CI step
fails. The end-to-end confirmation — that GitHub reports the run as
failed — requires pushing the branch, which has not been done.
