## Why this package stopped

`ENGINEERING.md` §7 and the CTO's standing instruction both say: if
implementation reveals a wider issue, stop and report rather than solve
it. This package hit one immediately.

**Production reports no backups.** Verified read-only:

```
supabase backups list --project-ref <production-ref>
→ walg_enabled: true, pitr_enabled: false, backups: [], physical_backup_data: {}
```

Supabase's published policy is that **Free Plan projects get no automatic
backups** and are told to export their own data with `db dump`; Pro and
above get daily backups with 7-day retention. The empty result is what a
Free Plan project looks like.

**The plan could not be determined without guessing.** Neither
`projects list` nor `orgs list` exposes a plan or tier field. Confirming
it requires the dashboard.

So the package's goal — *prove the backups are real* — currently has the
answer *there may be no backups to prove*. That is a materially different
finding from "the drill has not been run yet", and running a drill was
not the right next action. Confirming the plan is.

**This was the WP 00.06 lesson applied.** There, I inferred a general
truth about tooling from the repository's local state and was wrong.
Here, the evidence points strongly at Free Plan, and I have stated that
as *what the evidence looks like* rather than as fact, because the one
field that would settle it is not exposed to me.

## Findings

**1 · Production may have no recoverable backup at all.** Severity:
**critical**, if confirmed. The roadmap commits to migrating this
database across 26 epics. Doing that without a recoverable copy is a risk
that should be accepted knowingly, not by default. Blocks this package.

**2 · PITR is disabled and no physical backups exist.** Verified, not
inferred.

**3 · `db dump` is the only backup mechanism available on every plan**,
and it is what Supabase recommends for Free projects. Nothing currently
runs it on a schedule, so no off-Supabase copy of Klussie exists.

**4 · A restore drill copies personal data into a new place.** It needs a
short-lived, access-restricted, promptly destroyed scratch project — not
staging, which `ENVIRONMENTS.md` §6 forbids receiving production data.
Documented so the drill does not create a second unmonitored copy of the
customer database.

**5 · `.gitignore` does not cover `*.sql`.** A dump written into the
working tree would be committed. Called out in the document; **not
changed here**, because adding it is a `.gitignore` edit unrelated to
this package's deliverable and the safer instruction — write dumps
outside the tree — costs nothing.

## Rollback

Delete `docs/operations/DISASTER_RECOVERY.md`. Nothing else changed.

## Resolution so far

**Plan confirmed: Free.** Recorded as
[ADR-0016](../../docs/adr/0016-operate-production-on-free-plan-without-automatic-backups.md)
— operating without automatic backups is now a knowingly accepted risk
with a removal trigger, rather than an unexamined gap.

**A sixth finding emerged while acting on that.** Attempting to verify
the `db dump` fallback against staging — safe, no real customer data —
failed:

```
npx supabase db dump --linked -f schema.sql
→ LegacyDockerRunError: failed to run docker.
```

`db dump` runs `pg_dump` in a Docker container **even for a remote
database**. Docker is not installed, and neither are native `pg_dump` or
`psql`. So the one mechanism Free plan has is also unavailable:

| Mechanism | Available? |
|---|---|
| Supabase automatic backups | No — Free plan |
| PITR | No — disabled |
| `supabase db dump` | No — needs Docker |
| Native `pg_dump` / `psql` | No — not installed |

**There is no working backup mechanism of any kind.** This was verified,
not assumed, and it is why the package remains blocked after the
question that originally blocked it was answered.

## What unblocks this

1. **Choose the tooling** — Docker, native Postgres client tools, or a
   plan upgrade. Without one, no dump can be taken, so no drill can run.
2. **Take a dump** of production (a personal-data decision — §5 of the
   DR document).
3. **Create a scratch project**, restore into it, verify against known
   rows, record duration in §6, destroy it.

Steps 2 and 3 need the account owner. Step 1 needs a decision, and is
deliberately not made here — ADR-0016 explains why adding tooling was not
folded into the plan decision.
