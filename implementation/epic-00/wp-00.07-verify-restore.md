## Why this package stopped

`ENGINEERING.md` §7 and the CTO's standing instruction both say: if
implementation reveals a wider issue, stop and report rather than solve
it. This package hit one immediately.

**Production reports no backups.** Verified read-only:

```
supabase backups list --project-ref <production-ref>
→ walg_enabled: true, pitr_enabled: false, backups: [], physical_backup_data: {}
```

Supabase's published policy is that **Free Plan projects get no automatic
backups** and are told to export their own data with `db dump`; Pro and
above get daily backups with 7-day retention. The empty result is what a
Free Plan project looks like.

**The plan could not be determined without guessing.** Neither
`projects list` nor `orgs list` exposes a plan or tier field. Confirming
it requires the dashboard.

So the package's goal — *prove the backups are real* — currently has the
answer *there may be no backups to prove*. That is a materially different
finding from "the drill has not been run yet", and running a drill was
not the right next action. Confirming the plan is.

**This was the WP 00.06 lesson applied.** There, I inferred a general
truth about tooling from the repository's local state and was wrong.
Here, the evidence points strongly at Free Plan, and I have stated that
as *what the evidence looks like* rather than as fact, because the one
field that would settle it is not exposed to me.

## Findings

**1 · Production may have no recoverable backup at all.** Severity:
**critical**, if confirmed. The roadmap commits to migrating this
database across 26 epics. Doing that without a recoverable copy is a risk
that should be accepted knowingly, not by default. Blocks this package.

**2 · PITR is disabled and no physical backups exist.** Verified, not
inferred.

**3 · `db dump` is the only backup mechanism available on every plan**,
and it is what Supabase recommends for Free projects. Nothing currently
runs it on a schedule, so no off-Supabase copy of Klussie exists.

**4 · A restore drill copies personal data into a new place.** It needs a
short-lived, access-restricted, promptly destroyed scratch project — not
staging, which `ENVIRONMENTS.md` §6 forbids receiving production data.
Documented so the drill does not create a second unmonitored copy of the
customer database.

**5 · `.gitignore` does not cover `*.sql`.** A dump written into the
working tree would be committed. Called out in the document; **not
changed here**, because adding it is a `.gitignore` edit unrelated to
this package's deliverable and the safer instruction — write dumps
outside the tree — costs nothing.

## Resolution so far

**Plan confirmed: Free.** Recorded as
[ADR-0016](../../docs/adr/0016-operate-production-on-free-plan-without-automatic-backups.md)
— operating without automatic backups is now a knowingly accepted risk
with a removal trigger, rather than an unexamined gap.

**A sixth finding emerged while acting on that.** Attempting to verify
the `db dump` fallback against staging — safe, no real customer data —
failed:

```
npx supabase db dump --linked -f schema.sql
→ LegacyDockerRunError: failed to run docker.
```

`db dump` runs `pg_dump` in a Docker container **even for a remote
database**. Docker is not installed, and neither are native `pg_dump` or
`psql`. So the one mechanism Free plan has is also unavailable:

| Mechanism | Available? |
|---|---|
| Supabase automatic backups | No — Free plan |
| PITR | No — disabled |
| `supabase db dump` | No — needs Docker |
| Native `pg_dump` / `psql` | No — not installed |

**There is no working backup mechanism of any kind.** This was verified,
not assumed, and it is why the package remains blocked after the
question that originally blocked it was answered.

**Delivered**

| File | Contents |
|---|---|

| `docs/operations/DISASTER_RECOVERY.md` v2.0 | Strategy, coverage, schedule, RPO/RTO, backup and restore procedures |
| `docs/operations/POSTGRES_TOOLS_WINDOWS.md` | Step-by-step install and verification |
| `ENGINEERING.md` §8 | Pre-migration backup gate |

**The strategy, in one line:** native `pg_dump` over the session-mode
pooler plus `supabase storage cp` over the Storage API — no Docker, no
subscription, no paid tooling.

**Facts it rests on**, each verified by running the tool:

- Session pooler `aws-1-eu-west-1.pooler.supabase.com:5432` is
  IPv4-reachable and supports `pg_dump`; user format `postgres.<ref>`.
- `supabase storage ls|cp` needs `--experimental`, works **without
  Docker**, supports `--recursive`. Four buckets: `avatars`, `portfolio`,
  `request-photos`, `item-photos`.
- **`supabase db dump` excludes `auth` and `storage`.** Its own
  `--exclude-schema` list, read from `--dry-run`. A dump using its
  defaults contains **no user accounts** — which is why this strategy
  captures `auth` explicitly and does not use that command.
- **No Supabase Edge Functions exist.** `api/*.js` are Vercel serverless,
  tracked in git.

## Finding 9 · The pooler host is per project, not per region

The runbook hardcoded `aws-1-eu-west-1` — staging's host, generalised
into a constant. Production is on `aws-0-eu-west-1`. Both projects are in
`eu-west-1`.

The wrong host fails with `(ENOTFOUND) tenant/user postgres.<ref> not
found`, **which reads like a username error and is not one.** Determined
empirically with a deliberately invalid password, so no credential was
involved. Both hosts are now recorded, with instructions for finding a
new project's host.

## Finding 10 · Nine triggers make a naive restore actively wrong

This changed the backup design and is the most consequential finding of
the package.

A data-only restore fires every trigger, producing a database that re-ran
its own history rather than a copy of production: `handle_new_user`
inserting profiles, `handle_quote_sent` moving request statuses,
`handle_new_review` recomputing `pro_stats`, `handle_new_request` and
`handle_job_completed` re-emitting domain events.

**Resolved by `pg_dump --section`** — schema split into `pre-data`
(tables) and `post-data` (triggers, indexes, constraints, policies), so
data loads into a database that has no triggers yet.

**One trigger cannot be deferred.** `handle_new_user` is on `auth.users`,
which Supabase manages and which exists before any restore begins.
Mitigated with `--on-conflict-do-nothing`, and **explicitly listed as the
thing the drill must verify** — whether restored profiles keep their real
values or get overwritten by trigger defaults is not knowable on paper.

## What this package delivered

Klussie went from **no working backup mechanism of any kind** — not on
the platform, not locally — to a verified, executable backup path with a
documented restore procedure, without spending anything and without
adding Docker.

| Before | After |
|---|---|
| No platform backups (Free plan) | Unchanged — but no longer the whole story |
| `supabase db dump` unusable (Docker) | Native `pg_dump` 18.4, verified against both projects |
| No credential path | `pgpass.conf`, no password in any command or transcript |
| No restore procedure | Four-stage procedure, designed against the real trigger inventory |
| `auth` uncovered by any tooling | Captured explicitly — the one thing nothing else can rebuild |
| Trigger hazard unknown | Nine triggers enumerated; eight solved by ordering, one mitigated and flagged |
| No pre-migration gate | Gate defined and referenced from `ENGINEERING.md` §8 |

## What remains unproven

The restore itself. `DISASTER_RECOVERY.md` §8 states exactly what is
verified and what is not, and names the one known defect — whether
restored `profiles` survive `handle_new_user` or are overwritten by its
defaults. It is invisible without a drill and produces a database that
looks healthy.

**A drill is possible without a third project**, and is recorded in §8 as
an option rather than assumed: staging can be its own target, because WP
00.06 proved it rebuilds from empty in minutes. That involves no
production data and breaks no handling rule. Offered for a future
decision; not adopted here.

## Consequence carried forward

Epic 03 will backfill production with a backup that has never been
restored. That is materially safer than the position before ADR-0017 —
which was no backup at all — but *"we have a backup"* and *"we have a
proven backup"* are different claims. Recorded in
`DISASTER_RECOVERY.md` §10 so it surfaces when Epic 03 is planned.
