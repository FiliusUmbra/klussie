# WP 00.04 — Migrate one leaf module to TypeScript as proof

**Epic.** 00 — Engineering Foundations
**Status.** In review
**Branch.** `epic-00/wp-00.04-first-typescript-module`
**Complexity.** Low

---

## Goal

Prove the WP 00.03 toolchain on a real module with no dependents at risk.

## Migration step

Not a migration in the six-step sense — no data, no dual-write, no
read-switch. A file conversion.

## Architecture references

None. `docs/IMPLEMENTATION_ROADMAP.md` §11 defines the package.
`docs/engineering/ENGINEERING_STANDARDS.md` records that TypeScript
adoption is incremental, smallest and most-depended-on files first, never
a big-bang rewrite.

## ADR required?

**No.** Per `docs/adr/README.md`, an ADR records a decision that was
genuinely debatable, expensive to reverse, or pattern-setting. Adopting
TypeScript incrementally is already decided and recorded; this package
makes no new decision. Which module to convert is a low-stakes judgement,
reversible by a file rename, and sets no pattern others must follow.
Writing one here would dilute the index.

## Scope

**In scope**
- Convert `src/lib/reportReasons.js` and its test to TypeScript.

**Explicitly out of scope**
- Converting any other module. This is a proof, not a migration wave.
- Changing the module's behaviour, exports or comments.
- Touching the consumer — see Findings; it turned out not to be needed.
- The codebase-wide `.js` import convention — see Findings.

## Module selection

`reportReasons` was chosen on evidence, against the roadmap's criterion
of *"a real module with no dependents at risk"*:

| Candidate | Lines | Imports | Dependents |

Smallest blast radius in `src/lib`: zero imports, one consumer. It is

no schema, no consumer change, no dependency change. `git revert` on the

## Findings

**1 · Vite resolves `.js` import specifiers to `.ts` files. The
codebase's extension convention does not block TypeScript adoption.**

The codebase writes relative imports with explicit extensions — 84 with
`.js`, against 136 without. Both the test and the consumer import
`reportReasons.js`. The obvious expectation was that renaming the file to
`.ts` would break them and force the consumer to be edited.

Tested empirically rather than assumed: renamed the module, built with
every import unchanged, **exit 0**. TypeScript's `bundler` module
resolution accepts the same specifiers, so `npm run typecheck` also
passes.

This is worth recording because it removes a cost from every future
conversion. Migrating a module does **not** require touching its
consumers, which keeps later conversions small and keeps their diffs
honest. It is also why this package's file list matched the roadmap
exactly instead of growing.

**2 · Type annotations were kept faithful to runtime, not tightened.**

`reportReasonLabelKey` still accepts any string and still returns
`undefined` for an unknown code, because a code arriving from a stored
row genuinely may not be one this client knows — the module's existing
comment and test both say so. The lookup widens the record at the point
of access rather than narrowing the parameter, so no input is asserted
to be something it is not, and no runtime guard was added that would have
changed behaviour for inherited keys such as `toString`.

## Notes

**`as const` on `REPORT_REASONS`** derives the `ReportReason` type from
the codes rather than restating them, so they stay defined once. The
consumer's `REPORT_REASONS[0]` and `.map()` are unaffected by the array
becoming readonly.

**The completeness constraint is now enforced twice** — at compile time
by `Record<ReportReason, string>`, and at runtime by the existing test.
The test was already there and is not redundant: it is what protects the
guarantee for anything reaching the module from outside TypeScript.
