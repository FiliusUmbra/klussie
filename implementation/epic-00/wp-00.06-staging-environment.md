## Evidence — the migration chain is proven from empty

The account owner created an empty staging project and ran
`supabase db push --linked`. **All 17 migrations applied without
modification. None failed.**

Independently verified afterwards from this repository, read-only:

```
supabase migration list --linked
  → all 17 versions report local === remote (0001…0017)

supabase db push --linked --dry-run
  → {"upToDate": true, "migrations": []}
```

**Why this matters beyond the environment.** Until now every migration
had only ever run incrementally against one long-lived database, and
whether the seventeen could rebuild it from nothing was genuinely
unknown. It is now known, and the answer is yes — with **no file
modified** to make it work.

That retires Finding 3 and removes a real unquantified risk from every
schema epic that follows: Epic 01 onward can now rehearse against a
database built the same way production was, rather than hoping.

**It also proves the migrations are re-runnable end to end**, which the
repository had asserted for individual files (`0013`, `0015`) but never
for the chain.

## Why this package is blocked rather than complete

Creating a Supabase project requires dashboard access to the account,
an organisation, a region choice and a plan decision. It cannot be
performed from the repository, and it is not something to be done on the
account owner's behalf.

What is delivered is everything that *is* in the repository's power: the
runbook that makes the provisioning fast and ordered, the configuration
that selects an environment, and the checklist the acceptance criteria
are verified against. **The criteria are deliberately left unticked.**
Marking this package complete because its documentation exists would put
a false green against the prerequisite that guards every schema epic in
the roadmap.

## Findings

> **Findings 1 and 2 were wrong and have been corrected.** They were
> written from the repository's state — no CLI dependency, no
> `config.toml`, a diagnostic script that exists to infer schema state —
> and I generalised from that to "there is no CLI and no ledger." CTO
> investigation with CLI v2.114.0 showed otherwise, and the corrected
> facts are below, each verified by running the tool.

**1 · A migration ledger does exist — the CLI maintains it.** ~~Nothing
records which migrations have been applied.~~ `supabase db push` creates
`supabase_migrations.schema_migrations` in the target project and records
each migration as it lands, skipping what is already applied. Verified:
`migration list --linked` returned all 17 local migrations with
`remote: ""`, correctly reporting the fresh staging project as having
none applied.

**2 · The CLI is usable without installation or `config.toml`.**
~~Migrations must be pasted into the dashboard by hand.~~ `npx supabase`
fetches it; `link` succeeds without `config.toml`; `db push --linked`
works. `config.toml` configures the **local Docker stack** and vault
secrets — neither applies to a cloud-only workflow, which is why
`supabase status` fails without Docker and that failure is expected
rather than a defect. Linked projects are recorded in `supabase/.temp/`.

**3 · ~~The migration set has never been applied from empty.~~
RESOLVED.** All 17 applied cleanly to an empty staging project with no
file modified, and the result was verified independently — see Evidence.
The migration chain is proven.

**8 · Why this package's blocked deliverable was still worth shipping.**
The runbook was written before staging existed and the provisioning ran
against it without amendment, which is the outcome that justifies writing
a runbook rather than improvising. The one thing it got wrong — the CLI
and ledger — was corrected before anyone followed it, because the
correction pass happened while the package was still open. Worth noting
for future blocked packages: shipping the runbook early is what made the
error findable early.

**4 · `.env.local.example` omits `ANTHROPIC_API_KEY`.** Unchanged. Real
but unrelated to environment selection; not fixed here.

**5 · `0001`–`0017` filenames are accepted despite not being
timestamps.** The CLI documents `<timestamp>_name.sql` and compares only
the leading version, so the existing four-digit sequence parses and
orders correctly — verified by `migration list`. Future CLI-generated
files carry 14-digit timestamps and, because `0…` sorts before `2…`,
order after the existing sequence as intended. **The existing files must
never be renamed**: a version recorded in a ledger cannot change.

**6 · Production's ledger is unreconciled, and this is now a live
hazard.** Production's 17 migrations were applied by hand, so it has no
ledger table. The CLI would read that as "nothing applied" and attempt to
run all seventeen against a populated database. `migration repair
--status applied` writes ledger rows without executing SQL and is the
one-time fix — documented in `ENVIRONMENTS.md` §9, **not performed here**.

**7 · `supabase/.temp/` was untracked and not gitignored.** It holds the
linked project ref, organisation id and slug — per-machine state that
would otherwise have been committed, pushing one developer's environment
choice onto everyone. Checked for embedded credentials: none found.
Added to `.gitignore`.
