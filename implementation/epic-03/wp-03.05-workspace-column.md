# WP 03.05 — Add the workspace column to existing tables (add)

**Epic.** 03 — Workspace Engine
**Status.** Done
**Branch.** *(implemented directly; not yet branched — see WP 03.01's Notes)*
**Complexity.** Medium

---

## Goal

Every workspace-scoped existing table carries a `workspace_id` column,
nullable and unpopulated, ready for WP 03.06's backfill.

## Migration step

**Step 1 — `add`** (roadmap §3). Pure addition. No existing row, policy
or grant is touched.

## Architecture references

- `DATABASE_ARCHITECTURE.md` §5 — the tenancy rule: every record carries
  its workspace directly, not derived by joining through two other
  records
- `DATABASE_ARCHITECTURE.md` §6 — the Crossing Registry; Conversation's
  home partition is "the engagement or subject it is bound to"
- `DATABASE_ARCHITECTURE.md` §19 — request owned by the requesting
  workspace, quote owned by the offering workspace
- `SUPABASE_ARCHITECTURE.md` §5 — no cascading deletes anywhere (the
  foreign key added here has no `on delete` clause)
- `SUPABASE_ARCHITECTURE.md` §20 — every workspace-scoped table carries
  its workspace so the predicate is an indexed equality

## ADR required?

**No**, with one caveat recorded rather than decided in passing.
Thirteen of the fourteen tables considered have a citable rule — either
directly from a frozen document or, for `reviews` and `reports`, a
stated interpretation flagged as such in the migration's own header
rather than presented as a citation. `ai_usage_log` was deliberately
excluded rather than force a call — see Findings.

**Explicitly out of scope**

## Findings

**1 · `public.ai_usage_log` is deliberately excluded, not decided.**
Rate-limiting infrastructure keyed to a person, with self-scoped access
only. Genuinely ambiguous whether it is identity-scoped (a person's own
usage, following them across workspaces) or workspace-scoped (usage
incurred acting within a specific context) — nothing today depends on
resolving it, so this package did not force an answer. Whoever next
touches this table's tenancy should read `DATABASE_ARCHITECTURE.md` §5's
three levels before choosing.

**2 · `reviews` and `reports` follow a stated interpretation, not a
citation.** No frozen document says explicitly where a review or a
report row is homed — only where the *projection* computed from reviews
lives (`DATABASE_ARCHITECTURE.md` §19: reputation "computed from service
records and reviews," which is silent on the raw row). Assigned to the
reviewing/reporting (requesting) workspace by analogy with the request
they reference, and flagged as an interpretation in the migration's own
header so a future reader can tell the difference from a citation.

**3 · `conversations` and `messages` are a genuine bilateral crossing
that ADR-0025 did not name.** ADR-0025 enumerates six policy exceptions
surviving Epic 03 unchanged — three pre-engagement discovery, three
professional publication — and conversations/messages are neither: their
existing policies (`0001_init.sql`) are participant-based
(`customer_id`/`pro_id` on both sides), matching
`DATABASE_ARCHITECTURE.md` §6's Conversation entry in the Crossing
Registry exactly. This package assigns the column (requesting
workspace, per the registry's stated home partition) without touching
any policy — that is WP 03.10's problem, and it now has a citable answer
waiting for it rather than a rediscovery.

## Notes

**Why an index on an all-null column.** `SUPABASE_ARCHITECTURE.md` §20
makes the workspace predicate's index a stated performance requirement,
not a preference. Adding it now, while the column is empty, costs a few
kilobytes per table and means WP 03.10 lands on tables already ready for
it rather than depending on a later package remembering.

**Why a foreign key on an all-null column.** A foreign key on a nullable
column constrains only non-null values — free against an empty column,
and it means WP 03.06's backfill is checked by the database as it
writes, the same property `workspace.memberships`' own reference to
`workspace.workspaces` (WP 03.01) already relies on.
