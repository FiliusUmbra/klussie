# WP 03.02 — Add the membership helper

**Epic.** 03 — Workspace Engine
**Status.** Done
**Branch.** *(implemented directly; not yet branched — see WP 03.01's
Notes)*
**Complexity.** High

---

## Goal

An RLS policy — once WP 03.10 writes one — can ask "is the current
principal a live member of this row's workspace?" in a way that costs the
same regardless of how many rows are scanned.

## Migration step

**Not a six-step migration.** This is infrastructure the migration
pattern's later steps (dual-write, reconcile, switch reads) will depend
on, not a step in migrating an existing aggregate.

## Architecture references

- `SUPABASE_ARCHITECTURE.md` §6 — the isolation predicate; "a single
  security-definer, `STABLE` helper... once per statement rather than
  once per row"
- `SUPABASE_ARCHITECTURE.md` §20 — the platform's first performance
  concern; "a policy that runs a correlated subquery per row turns every

## Scope

**In scope**

- `api` schema, created and granted `USAGE` to `authenticated` only.
- `workspace.current_memberships()` — the engine's own logic, `STABLE`,
  not `SECURITY DEFINER`, granted to nobody.
- `api.current_workspace_memberships()` — the delegate, `STABLE`,
  `SECURITY DEFINER`, parameterless, granted `EXECUTE` to `authenticated`
  only.
- `supabase/diagnostics/VERIFY_MEMBERSHIP_HELPER.sql`, including a
  behavioural probe and once-per-statement evidence for human review.

**Explicitly out of scope**

- **Any RLS policy** — WP 03.10, which must use
  `api.current_workspace_memberships()` as an uncorrelated subquery, not
  as a per-row scalar check (see Finding 1).
- **Relocating Epic 02's existing functions** —
  `current_identity()`, `resolve_identity_display()`,
  `emit_domain_event()` stay in `public` under ADR-0023 and ADR-0004.
- **Scope resolution against a location tree** — no tree exists until
  Epic 06. The helper returns the scope recorded on the membership;
  nothing resolves it.
- **Capability resolution** — no Capability engine exists until Epic 04.

**The `EXPLAIN` evidence, captured against staging:**

```
 Hash Semi Join (actual time=0.108..0.109 rows=0 loops=1)
   ->  Function Scan on pg_catalog.generate_series g (actual time=0.097..0.097 rows=1 loops=1)
   ->  Hash (actual time=0.001..0.001 rows=0 loops=1)
         ->  Limit (actual time=0.001..0.001 rows=0 loops=1)
               ->  Function Scan on api.current_workspace_memberships (never executed)
                     Function Call: api.current_workspace_memberships()
```

Stronger than expected. The planner places
`api.current_workspace_memberships()` on the **build side of a hash semi
join** — `loops=1` — rather than as a per-row filter on the probe side.
This is the structural property Finding 1 predicted: the delegate is
evaluated once regardless of how many rows the left-hand scan produces,
confirmed on a real database rather than argued from documentation.
(`generate_series(1, 1000)` shows `rows=1` here because the probe uses
`limit 0` on the right-hand side — a shape-only check with no
authenticated session in a `psql` connection — which the planner
short-circuits to zero rows needed on the left before scanning it. The
join shape is the evidence; the row counts are an artifact of the probe
having nothing to match. The behavioural probe in check 3, in the same
run, is what proves the delegate returns the *correct* rows when a real
`auth.uid()` is simulated.)

## Rollback

```sql
revoke execute on function api.current_workspace_memberships() from authenticated;
drop function api.current_workspace_memberships();
drop function workspace.current_memberships();
revoke usage on schema api from authenticated;
drop schema api;
```

**No data is lost.** No table was created; the two functions are pure
reads with no side effect. Dropping `api` has no consequence for
`public`, which this package never touched.

## Findings

**1 · The delegate's originally accepted shape cannot achieve
once-per-statement evaluation, and `STABLE` does not prevent this.**

ADR-0026, as accepted, named `api.is_workspace_member(uuid)` — a scalar
function taking a workspace id. Building it against this package's own
acceptance condition (ADR-0024: *"evidence of once-per-statement, not the
marking alone"*) found the shape fails by construction, not by
implementation error.

`STABLE` permits the planner to evaluate a function once per statement
**only when its argument does not vary per row**. Current Supabase
guidance states this directly: *"STABLE functions may be evaluated once
per query rather than once per row — but only if the planner can prove
the value is constant within the query… Functions marked as stable still
need to be wrapped in a subquery in order for Postgres to properly cache
the result."* Used the natural way in a policy —

```sql
using (api.is_workspace_member(workspace_id))
```

— the argument is the scanned row's own column, different on every row.
`STABLE` does not cache across different arguments; the function is
re-invoked per row, re-running the join inside
`workspace.current_memberships()` every time — the exact "correlated
subquery per row" failure `SUPABASE_ARCHITECTURE.md` §20 names as the
platform's most likely catastrophic degradation. **Built as originally
specified, this package would have shipped, under a `STABLE` marking,
the precise failure mode the marking exists to prevent.**

The fix: a **parameterless** delegate — `api.current_workspace_memberships()`
— depending on nothing but `auth.uid()`, constant for the whole
statement. Used as an uncorrelated subquery
(`workspace_id in (select workspace_id from api.current_workspace_memberships())`),
the planner can recognise it as independent of the outer row and evaluate
it once. `api.is_workspace_member(uuid)` was not built. Recorded in full,
with citation, in ADR-0026's "As implemented" section — this is a
correction to an already-accepted ADR, made before any RLS policy could
depend on the wrong shape, and surfaced for approval rather than decided
in passing, per this project's standing rule on architectural deviations
found during implementation.

**2 · `workspace.current_memberships()` needing `workspace.memberships`
to exist made WP 03.01 a hard prerequisite, not a scheduling
preference.** See WP 03.01's own Finding 1. Both packages are recorded
separately because they have separate scope, separate acceptance criteria
and separate rollback points, even though they landed in the same
session.

## Notes

**Why the split (logic in `workspace`, delegate in `api`) rather than one
function in `api`.** `emit_domain_event()` and `resolve_identity_display()`
are engine *operations*, invoked by application code and replaceable one
caller at a time. The membership predicate is the *substrate of RLS* —
referenced by every policy on every workspace-scoped table, permanently.
Putting its logic in a client-reachable schema would migrate tenancy
enforcement itself into `api`, and every later engine would face the same
temptation. The split costs one indirection and keeps each engine's logic
inside the schema that owns it.

**Every RLS policy from WP 03.10 onward must call
`api.current_workspace_memberships()` as a subquery, never as a scalar
per-row check.** This is now the load-bearing convention the whole
epic's performance depends on, and it is not enforced by any constraint
the database can check — only by every future policy author having read
Finding 1. Worth a lint-style structural test over future RLS migrations
if this project ever writes one; not built here, as it would be scope
beyond this package.
