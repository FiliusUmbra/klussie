# WP 03.04 — Backfill one Professional Workspace per existing pro profile

**Epic.** 03 — Workspace Engine
**Status.** Done
**Branch.** *(implemented directly; not yet branched — see WP 03.01's Notes)*
**Complexity.** Medium

---

## Goal

Every existing, non-erased `pro_profiles` row has exactly one
Professional Workspace and an owner membership, and every dual-role
person (already backfilled a Personal Workspace by WP 03.03) gains the
second without either workspace touching the other.

## Migration step

**Step 2 — `backfill`** (roadmap §3). Same shape as WP 03.03: the new
structure is populated; `public.pro_profiles` is read, not written.

## Architecture references

- Roadmap §14 (03.04) — "the dual-role case that motivates the whole
  model"
- `PLATFORM_DOMAIN_MODEL.md` §27 — additional workspaces "created when
  there is something real to put in them"
- [ADR-0023](../../docs/adr/0023-identity-display-resolution-versus-row-visibility.md) —
  measured against staging: "`business_name` is frequently the person's
  own name" for flexi pros, which is why the name fallback exists
- `0001_init.sql` — `business_requires_details`: a `business` pro_type
  requires `business_name`; a `flexi` one usually has neither

## ADR required?

No. Same posture as WP 03.03 — ADR-0022 already governs identifier
minting, accepted as that package's prerequisite.

## Scope

**In scope**

- One statement backfilling `workspace.workspaces` (type
  `professional`, name `coalesce(business_name, full_name, 'My
  Business')`) and `workspace.memberships` (role `owner`, state
  `active`) per non-erased identity with a `pro_profiles` row.
- `supabase/diagnostics/VERIFY_BACKFILL_PROFESSIONAL_WORKSPACE.sql`.

**Explicitly out of scope**

- **Populating `workspace_id` on `pro_profiles` or any other table** —
  WP 03.06.
- **A `pro_profiles` row with no matching identity** — not raised as an
  error here; WP 03.07's reconciliation is the package built to catch
  this class of discrepancy against real data.

## Rollback

```sql
delete from workspace.memberships
where workspace_id in (select id from workspace.workspaces where type = 'professional');
delete from workspace.workspaces where type = 'professional';
```

**Data is lost, and that is a property of this step**, same as
WP 03.03. No Personal Workspace is touched by this rollback — it
targets `type = 'professional'` specifically.

## Findings

**1 · The diagnostic's synthetic probe hit a real foreign key on first
run.** `public.profiles.id` references `auth.users`, which a synthetic
identity has no row in. Fixed by suspending trigger/FK enforcement for
the synthetic insert (`set local session_replication_role = replica`) —
the identical technique `VERIFY_IDENTITY_BACKFILL.sql` already
established for this exact situation, so this is a known pattern rather
than a new one. **2 · Second finding, same run:** the synthetic `business`
pro also needed a `vat_number` to satisfy `business_requires_details`,
missed on the first attempt. Both caught by actually running the
diagnostic against a live database rather than reviewing it by eye —
consistent with this project's stated discipline that a check is trusted
once it has been shown able to fail, not before.

## Notes

**Staging's three real `pro_profiles` rows exercised both name-fallback
branches without any synthetic help.** Two `flexi` pros with no
`business_name` (falling back to their own name) and one `business` pro
with one (`"Sparse"`) — real coverage of the rule this package's
riskiest decision depends on, not merely a happy-path assumption.
