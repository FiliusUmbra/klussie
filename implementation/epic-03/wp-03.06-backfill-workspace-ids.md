## Impact

**Database.** An UPDATE-only backfill across thirteen tables. On
staging: three real rows populated (`pro_profiles`, `pro_stats`,
`pro_services` — the only tables with real data); the remaining ten
tables are empty on staging and therefore updated zero rows for real
data, proven correct instead by a full synthetic scenario.

**Backend.** None. **Frontend.** None.

**Behaviour.** None observable — see Findings for the one real, checked
side effect.

## Tests

`supabase/migrations/__tests__/backfillWorkspaceIds.test.js` — seven
structural assertions covering all thirteen tables as one parametrised
set, plus the two checks specific to this package's real risk:

| Test | What it protects |
|---|---|
| Derives `service_request_photos`, `conversations` and `messages` from their parent, not from identity | The one place this backfill differs in *shape*, not just source table — getting this wrong would silently resolve these three to nothing (`NULL parent → NULL child`, which passes every `IS NULL` guard on a re-run instead of erroring) |

real-data correctness for the three populated tables (check 1), a full
synthetic scenario exercising all thirteen tables and the derived
chain's ordering in one pass (check 2), idempotency (check 3), cleanup
(check 4).

## Findings

**1 · The diagnostic's synthetic population needed four rounds of
correction against the real schema before it ran clean.** Each caught
by actually executing against staging, not by review:

- Two UUID literals used mnemonic letter suffixes (`e0se`, `e0sr`, `e0qt`,
  etc.) containing non-hex characters (`s`, `r`, `q`, `t`, `v`, `m`,
  `h`, `i`) — PostgreSQL rejected them as invalid UUID syntax. Fixed by
  replacing every such suffix with valid hex.
- `portfolio_items` requires `image_url` and `storage_path`, not the
  guessed `title`; `testimonials` uses `client_name`/`quote_text`, not
  `author_name`/`body`.
- `quotes` has `sent_at`, not `created_at`.
- `service_requests_directed_complete` (migration 0013) requires
  `directed_pro_id`, `directed_until` and `auto_accept_max` either all
  null or all set — and `directed_until` defaults to `now() + 24h`
  (migration 0014), so an insert that omits it fails the constraint
  unless the default is explicitly overridden with `null`. This is the
  identical class of defect migration 0014 itself was written to fix
  ("the unit tests could not catch it... a missing column default is
  only observable against a real database") — caught here the same way,
  by running against a real one.

**2 · The `service_requests_set_updated_at` trigger fires during this
backfill, and was checked before writing the migration, not after.**
Confirmed by grep that `src/lib/requests.js` fetches `updated_at` but no
component renders or sorts by it. Documented in the migration's own
header as a deliberate, considered acceptance rather than an oversight.

## Notes

**The highest structural risk in the epic, by the roadmap's own
ranking, and the one place a silent defect would have been genuinely
silent.** A wrong join, a missing `IS NOT NULL` guard on a parent
lookup, or a reversed ordering in the derived group would not have
raised an error anywhere — it would have produced a `NULL` or a
wrong-but-present `workspace_id`, indistinguishable from correct until
WP 03.10's RLS policies started hiding or exposing the wrong rows to the
wrong workspace. This is exactly the failure mode WP 03.07's
reconciliation exists to catch before that can happen, and exactly why
this package's own diagnostic went to the length of exercising every
one of the thirteen tables and the full derived chain in one synthetic
pass rather than trusting the three real rows staging happened to hold.
