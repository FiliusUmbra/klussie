# WP 03.03 — Backfill one Personal Workspace per existing identity

**Epic.** 03 — Workspace Engine
**Status.** Done
**Branch.** *(implemented directly; not yet branched — see WP 03.01's Notes)*
**Complexity.** Medium

---

## Goal

Every existing, non-erased identity has exactly one Personal Workspace
and an owner membership.

## Migration step

**Step 2 — `backfill`** (roadmap §3). The new structure is populated;
nothing reads it yet. `identity.identities` is untouched — this package
only writes to `workspace.workspaces` and `workspace.memberships`.

## ADR required?

**No new ADR.** ADR-0022 already governs this exactly, and was accepted
(not modified) as the prerequisite step of this same session, per rule 6
of the autonomous-mode instructions this package was built under: an
*accepted* ADR is never modified without proposing the change first, but
accepting a still-*Proposed* one — with an honest correction to a factual
claim inside it — is the acceptance procedure itself, not a modification
of an accepted document.

## Scope

**In scope**

- One statement backfilling `workspace.workspaces` (type `personal`,
  name `"My Home"`) and `workspace.memberships` (role `owner`, state
  `active`) per non-erased identity.
- `supabase/diagnostics/VERIFY_BACKFILL_PERSONAL_WORKSPACE.sql`.

**Explicitly out of scope**

- **Professional Workspaces** — WP 03.04, a separate backfill over
  `pro_profiles`.
- **Populating `workspace_id` on any existing table** — WP 03.06, which
  needs this package's workspaces to exist as targets but does not run
  as part of it.
- **Renaming a workspace** — "My Home" is a stated default; "chosen by
  its members" (§5) is a product feature this backfill does not build.
- **`workspace.membership_history`** — nothing writes to it yet, per
  WP 03.01's own stated scope; this package does not change that.

## Impact

**Database.** A backfill. Real rows written to `workspace.workspaces`
and `workspace.memberships` — five workspaces, five memberships on
staging, one per live identity.

**Backend.** None. **Frontend.** None.

**Behaviour.** None — this package is behaviour-preserving. Nothing
reads the new rows; no request context resolution exists yet (WP 03.09);
no RLS policy references workspace scoping (WP 03.10).

## Tests

`supabase/migrations/__tests__/backfillPersonalWorkspace.test.js` —
eight structural assertions, mirroring `identityBackfill.test.js`'s
shape for the same class of package. The two that carry the highest
risk (roadmap's risk register item 1 — "Epic 03 backfill assigns rows to
the wrong workspace"):

| Test | What it protects |
|---|---|
| Mints the workspace id once and reuses it for both inserts | Two independent mints could disagree, leaving a membership pointing at a workspace that does not exist, or a workspace with no owner |
| Checks for an existing *personal, owner* membership specifically | A check for "any workspace" would skip someone who already has a Professional Workspace (WP 03.04) when they still need a Personal one |

`supabase/diagnostics/VERIFY_BACKFILL_PERSONAL_WORKSPACE.sql` — four
checks against staging: the acceptance criterion against real data
(check 1, all five live identities), a synthetic population proving
exact attribute values, ordering and the erasure exclusion (check 2),
idempotency (check 3), and cleanup verification (check 4).

## Rollback

```sql
delete from workspace.memberships
where workspace_id in (select id from workspace.workspaces where type = 'personal');
delete from workspace.workspaces where type = 'personal';
```

**Data is lost, and that is a property of this step, not an oversight.**
Roadmap §3: steps 1–4 "roll back by dropping what was added" — the
identifiers minted here are permanent per ADR-0022 and §8, so a rollback
does not recover them; a re-run after rollback mints fresh ones. No
existing table (`identity.identities`, `public.*`) is touched by this
package or by its rollback.

## Notes

**Highest-risk package in the roadmap so far, by the risk register's own
ranking.** Roadmap §15 risk 1 names exactly this backfill. Handled by
the same discipline Epic 02 established for identity: a real-data check
against everything staging holds (not a sample), plus a synthetic
population precise enough to assert exact attribute values, ordering,
and the erasure exclusion — proven able to fail (an erased identity
correctly produced zero rows in the synthetic check, and re-running
against the same population changed nothing) rather than assumed correct
because the happy path passed.

**ADR-0022's acceptance is recorded as part of this package rather than
as a separate one**, because it was the prerequisite this specific
package was blocked on and nothing else in the epic needed it resolved
first. Both changes are in the same commit-eligible unit of work.
