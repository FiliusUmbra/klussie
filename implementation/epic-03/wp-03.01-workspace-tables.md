# WP 03.01 — Create workspace and membership tables (add)

**Epic.** 03 — Workspace Engine
**Status.** Done
**Branch.** *(implemented directly; not yet branched — see Notes)*
**Complexity.** Medium

---

## Goal

The workspace and membership structure exists; nothing reads or writes
it.

## Migration step

**Step 1 — `add`** (roadmap §3). Pure addition. No existing table is
touched, no existing behaviour changes.

## Architecture references

- `PLATFORM_DOMAIN_MODEL.md` §5, §7 — what a workspace has regardless of
  type; what a membership carries (identity, workspace, role, optional
  scope, state, validity period); the four states verbatim
- `DATABASE_ARCHITECTURE.md` §9 — workspace: archived, never deleted;
  owned by its owner-role members, not a column
- `DATABASE_ARCHITECTURE.md` §10 — membership: "append-only history +
  mutable current"; both read directions are hot
- `SUPABASE_ARCHITECTURE.md` §4 — mutability classes; "membership
  history" named explicitly under Append-only, "workspace (archival)"
  under Soft-retire
- `SUPABASE_ARCHITECTURE.md` §5 — no foreign key from a durable record to
  identity; no cascading deletes anywhere
- `SUPABASE_ARCHITECTURE.md` §3 — UUIDv7, application-generated, no
  database default

## ADR required?

**No.** Every property is stated in a frozen document. The one departure
from a literal reading of roadmap §14 — three tables instead of "the
workspace and membership tables" (singular pairing) — is not a judgement
call; §4 names the append-only history as a distinct class from the
mutable current, which cannot be one table without violating the
Append-only enforcement mechanism (withheld privileges plus a guard
trigger) on rows that also need `UPDATE`.

## Scope

**In scope**

- `workspace.workspaces` — id, type, name, timestamps, `archived_at`.
- `workspace.memberships` — id, workspace_id (FK), person_ref (no FK),
  role, scope, state, expires_at, timestamps.
- `workspace.membership_history` — append-only, guard-triggered, no FK to
  identity.
- `UPDATE` granted on the two mutable tables; `DELETE` withheld
  everywhere.
- RLS enabled on all three, no policies.
- `supabase/diagnostics/VERIFY_WORKSPACE.sql`.

**Explicitly out of scope**

- **Any backfill** — WP 03.03, WP 03.04. All three tables are empty.
- **The membership helper** — WP 03.02, landed alongside this package by
  explicit approval because it cannot be built without these tables; see
  that package's own record.
- **Any RLS policy** — WP 03.10, gated by ADR-0025.
- **Populating `membership_history`** — nothing writes to `memberships`
  yet, so there is nothing to record. The mechanism that keeps the two in
  step is a decision for whichever package writes there first.
- **A uniqueness constraint on `(person_ref, workspace_id)`** — a person
  may hold a second membership after leaving one; deciding how re-joining
  works belongs to the engine that implements invitations.

## Impact

**Database.** Additive. Three tables, one guard trigger, explicit
grants, RLS enabled. One foreign key direction only (memberships/history
→ workspaces); none toward identity.

**Backend.** None. **Frontend.** None.

**Behaviour.** None — this package is behaviour-preserving. Nothing
reads or writes the tables, no client role can reach them, and every
existing flow is unaffected.

## Tests

`supabase/migrations/__tests__/workspace.test.js` — thirteen structural
assertions. The two that carry the epic's hardest rules:

| Test | What it protects |
|---|---|
| Declares no foreign key from memberships or history to identity | The same defect identity.test.js exists to catch, now in a second table: the obviously-correct-looking `references identity.identities` that makes erasure impossible or destructive |
| Enforces membership_history as append-only with a guard trigger | Mirrors `platform.audit_records`' pattern (migration 0022) — a table recording "who had access to what, when" is exactly the one a quiet correction would be worst on |

Plus: exactly three tables created guardedly; no default on any primary
key; correct FK shape (memberships → workspaces, history → memberships);
the four membership states named verbatim; no check constraint
enumerating role names (deliberately open vocabulary); UPDATE granted
only where mutable; no DELETE anywhere; RLS on with no policy; nothing
granted to client roles; `public` untouched; no uniqueness constraint on
the person/workspace pair.

`supabase/diagnostics/VERIFY_WORKSPACE.sql` — five checks against
staging, including a written-and-rolled-back probe that the append-only
guard trigger actually fires (not merely that it exists).

## Rollback

```sql
drop table workspace.membership_history;
drop table workspace.memberships;
drop table workspace.workspaces;
drop function workspace.membership_history_reject_mutation();
```

Then delete the migration, the diagnostic and the test. **No data is
lost.** All three tables are empty and nothing references them from
outside `workspace` — `VERIFY_WORKSPACE.sql` check 5 verifies rather than
assumes this for the identity direction specifically.

## Findings

**1 · This package was not the one scheduled for this session, and
building the one that was is impossible without it.** WP 03.02 (the
membership helper) resolves `workspace.memberships` — a `language sql`
function is validated against real objects at creation time, so it
cannot be created against a table that does not exist. Roadmap §14
already sequences 03.01 before 03.02 for this reason; the sequencing
was not followed by the original plan for this session, and was
corrected by explicit approval before either package was written, rather
than decided in passing.

**2 · No partial index on `workspaces.archived_at`, despite §4 naming one
for the Soft-retire class.** §4's general rule is "retired-at column,
partial indexes over live rows," but there is no query yet needing one —
the same restraint `identity.identities` held in Epic 02 ("there is no
query yet"). Added when a real query does.

## Notes

**No `owner_id` column on `workspace.workspaces`.**
`DATABASE_ARCHITECTURE.md` §9: "Owned by its owner-role members" —
plural, expressed entirely through a membership row with `role =
'owner'`. A column-based owner would be a second answer to the same
question, which `PLATFORM_DOMAIN_MODEL.md` Rule 11 (one permission path)
rules out.

**`scope` is `jsonb`, not a typed column.** No location tree exists until
Epic 06, and committing to a shape before the Location engine defines one
would be guessing. ADR-0026 already describes this column as "the scope
recorded on the membership" — inert until Epic 06 gives it a real shape.

**Role has no check constraint, unlike state.** State's four values are
closed and named verbatim in the domain model. Role vocabulary differs
per workspace type and the domain model names future custom roles for
enterprises as an explicit direction of evolution — a closed list here
would need revisiting the moment Epic 03's backfill runs.
