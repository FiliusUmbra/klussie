# WP 03.08 — Add the workspace engine contract

**Epic.** 03 — Workspace Engine
**Status.** Done
**Branch.** *(implemented directly; not yet branched — see WP 03.01's Notes)*
**Complexity.** High

---

## Goal

The Workspace engine can resolve a caller's context for one workspace,
decide whether a permission is granted, and explain the decision —
roadmap §14's three-part description of this package, met in full.

## Migration step

**Not a six-step migration.** Infrastructure — like WP 03.02, this
builds a contract nothing calls yet. Not wired into request handling
(that is WP 03.09).

## ADR required?

No new ADR. ADR-0027 (accepted the same session, before this package)
already decided the vocabulary; this package implements it.

## Scope

**In scope**

- `workspace.role_permissions` — the vocabulary as configuration, seeded
  with ADR-0027's three preset tables (53 rows).
- `workspace.resolve_context()`, `workspace.decide_permission()` — the
  engine's own logic.
- `api.resolve_workspace_context()`, `api.decide_permission()` — the
  delegates `authenticated` calls.
- `supabase/diagnostics/VERIFY_WORKSPACE_PERMISSION_VOCABULARY.sql`.

**Explicitly out of scope**

- **Wiring into request handling** — WP 03.09.
- **Any other engine's business-action permissions** — ADR-0027's own
  scoping boundary; Property, Work, Knowledge and Commerce each define
  their own when their epic is planned.
- **Custom roles** — `role_name` stays unconstrained (matching
  `workspace.memberships.role`), but no mechanism for a workspace to
  define its own role exists yet; §7 names it as a future direction,
  not something this package builds.

## Impact

**Database.** Additive. One table (53 seeded rows), four functions, two

**Backend.** None. **Frontend.** None.

**Behaviour.** None — this package is behaviour-preserving. Nothing

## Tests

`supabase/migrations/__tests__/workspacePermissionVocabulary.test.js` —
twelve structural assertions. The two that carry the package's real
risk:

| Test | What it protects |
|---|---|
| Seeds Owner/Administrator with all twelve, in every preset that has one | A missed row here means the top role in some preset is silently missing a permission — the exact failure mode a permission system must never have |
| `decide_permission` joins with `LEFT JOIN` throughout | An inner join anywhere in the chain would turn "no membership" into zero rows instead of one explained `granted = false` row — silently reintroducing the ambiguity §7's deny-by-default property exists to remove |

`supabase/diagnostics/VERIFY_WORKSPACE_PERMISSION_VOCABULARY.sql` — five
checks against staging: grant posture, RLS posture, the seed against
real data (53 rows, exact composition), and a full behavioural proof —
granted, denied, and no-membership-at-all, each decision explaining
itself correctly.

## Rollback

```sql
revoke execute on function api.decide_permission(uuid, text) from authenticated;
revoke execute on function api.resolve_workspace_context(uuid) from authenticated;
drop function api.decide_permission(uuid, text);
drop function api.resolve_workspace_context(uuid);
drop function workspace.decide_permission(uuid, text);
drop function workspace.resolve_context(uuid);
drop table workspace.role_permissions;
```

**No data is lost beyond the seed table itself**, which is
configuration, not a record of anything that happened — dropping it
loses no history.

## Findings

**1 · The diagnostic's own arithmetic was wrong on first run, not the
migration.** Check 3 asserted `membership.own.view` is held by eleven
roles; the real count, and the correct one, is twelve (3 Personal + 4
Professional + 5 Business). The seed was right; the check's expectation
was miscounted. Caught immediately by running against staging rather
than trusting the arithmetic on review — the same discipline that has
caught a defect in every diagnostic written this session.

## Notes

**`decide_permission` taking arguments does not repeat WP 03.02's
performance finding, and the migration says so explicitly** rather than
leaving a future reader to wonder. The earlier finding was about a
function called once per *scanned row* inside an RLS policy predicate.
`decide_permission` is a point query — called once, by something asking
about one specific action — and must never be given a role inside a
row-visibility policy. Recorded in the migration header and in ADR-0027's
"As implemented" section so the distinction survives independently of
this record.

**This closes Epic 03's foundation work.** WP 03.01–03.08 are all
additive or read-only; nothing has changed what any existing user sees.
WP 03.09 (resolve request context once, gated by ADR-0024) is the first
package that begins wiring any of this into what the running application
actually does.
